# Structured Interfaces：让语言模型查询场景图，而不是背下整张图

> 状态：技术精读 · ICRA 2026 作者公开稿与 arXiv v1 附录 · 未复现

## 一句话

把已有三维场景图放进图数据库，向语言模型开放 Cypher 查询工具，让关系遍历和距离计算在数据库执行，再返回少量带实体 ID 的结果，可同时提高大图上的问答与指令落地准确率，并显著压缩输入上下文。

## 它要解决的问题

人说“把院子里离车最近的包拿来”，机器人需要先确定哪个院子、哪辆车、哪个包，再把语言变成自己的任务目标。三维场景图是为此组织世界信息的一种表示：节点存对象、可通行位置、房间或区域，边存邻接、包含和其他关系，属性存类别、位置与包围盒。

直接把整图序列化成 JSON 或文本，能让模型读取节点，却把三件事同时交给了模型：从很长上下文找相关项，跨层追踪对象属于哪个区域，以及用坐标算距离。图越大，输入越长，正确结论依赖的信息也可能相隔越远。论文的大图包含 314 个物体、15,944 个二维可通行位置和 124 个区域，其复杂度主要来自空间结构，而非几百个物体的名称。

本文的任务从**已经构建好的场景图**开始。输入为用户问题或指令，输出有两类：关于场景的答案，或用图中符号实例化的 PDDL 目标。PDDL 是把状态、动作条件与目标写成逻辑谓词的规划语言；这里主要评估目标翻译，规划器再决定怎样实现目标。这个分工让研究问题聚焦于场景表示与语言模型之间的接口。

## 核心想法

作者把检索增强生成改成结构化查询。检索增强生成是先从外部存储取出问题所需的信息，再把结果交给模型作答；常见实现依靠向量相似度，本文改为让模型生成图查询语句。

接口采用 Cypher，一门针对图数据的声明式语言：描述“找满足哪些节点类型和关系的结果”，由数据库决定怎样搜索。模型负责把人的指代翻译成查询条件，Neo4j 数据库负责关系匹配、计数与几何计算，模型再把查询结果组装成答案或规划目标。图和数字计算由显式程序承载，模型上下文只接收相关结果。

这比固定的检索前处理多了一层反馈。模型可以看到查询返回的空集、结果或错误，再决定继续查还是回答。论文称这种方式为 agentic，即模型自行选择工具调用及后续步骤。实验还比较只能查询一次的版本，以及编写 Python 访问场景图 API 的版本，用来区分“外置计算”与“专门查询接口”的贡献。

[判断] 对场景编译器而言，核心资产不是再设计一种漂亮的图画法，而是**类型化世界模型、可执行查询语义和有界返回结果**。查询是任务相关的场景投影：同一数据库既能返回物体 ID 集合，也能返回距离、数量或空间位置，而不用每个问题都重新展示全部地图。

## 机制

**1. 用本体把世界模型的字段和关系解释清楚。**

本体在这里指系统允许哪些实体类型、属性和连接规则。论文采用 Hydra 场景图的子集，包括对象、二维 MeshPlace、三维 Place，以及房间或室外区域。MeshPlace 是地表上可通行的小块区域，Place 则表示三维自由空间的位置。跨层 CONTAINS 边表示包含，同层边表示连接。

节点有 nodeSymbol、class、center 等属性。提示词明确区分 O 表示对象、R 表示区域、P 表示二维可通行位置、p 表示三维位置，并强调大小写。它还列出可用类别、边类型、查询规则和规划谓词。这样“院子里的包”可以转换为区域到位置再到对象的关系，而无需模型猜测数据库的组织方式。

**2. 从语言产生查询，再让数据库做确定性计算。**

一条典型模式是 MATCH (r:Room)-[:CONTAINS*]->(o:Object)，再筛选 r.class 和 o.class，返回 o.nodeSymbol。星号表示沿一条或多条包含边寻找后代，因此能跨过中间位置层。空间条件可用 point.distance，计数可用 COUNT。数据库返回的 ID 继续用于目标谓词，形成从语言指代到地图符号的链路。

**示例数值：最近的包。** 假设区域 R2 包含 P4、P5；P4 中有包 O7，坐标 (3,4,0)，P5 中有包 O9，坐标 (6,8,0)，用户位置为 (0,0,0)。先沿 CONTAINS 找到这两个包，再计算距离：O7 为 √(3²+4²)=5 m，O9 为 √(6²+8²)=10 m，按距离升序取一个结果即可得到 O7。若用户要“把包带到 PStart”，输出目标为 (object-in-place O7 PStart)。这个目标保留实体引用，具体路径、抓取与搬运由规划和执行系统处理。坐标和 ID 为教学示例，论文没有报告这个例子的单独成绩。

ID 的价值在于跨查询和输出阶段保持引用一致。例如把 O7 的 class 从 bicycle 改为 bag，依然能用 O7 查到原来的空间位置。论文的实体 symbol 满足一次任务中唯一引用的需要；跨建图会话、物体重识别和节点合并后的持久身份需要底层图维护策略，本文没有测试这种稳定性。

**3. 把查询返回结果加入后续上下文。**

原文 §IV 的过程可写成：用户任务与本体描述构成初始提示 X；模型输出查询 q；数据库执行 q 得到 r；将 q、r 接回上下文，模型继续生成，直到给最终答案。附录完整提示示例最多允许五次查询，并要求每次查询前说明思路。

非 agentic 对照强制恰好一次查询：先让模型生成工具调用，再用其返回结果生成答案。这个对照改变了纠错和继续检索的机会，因而能测多轮工具反馈是否有用。Python 对照也可多轮，但使用 spark_dsg 的专用对象 API，要处理节点、属性对象、层与 ID 类型。Cypher 将这些操作压缩成更接近关系问题的声明式表达。

**4. 输入结构与输出格式都是接口的一部分。**

提示词由本体、类别表、接口描述、可选 PDDL 域、少量输入输出示例、用户问题和输出格式约束组成。问答输出使用 SLDP 小语言，支持字符串、数字、点、列表、集合、字典；用 answer 标签区分最终答案和中间工具调用。这样“这些对象有哪些”和“按距离排序”分别可使用集合和列表，评测器能保留两种答案语义的区别。

附录 §B 定义自动比较：集合忽略顺序，列表保留顺序；数值误差容差为 0.01，点按无穷范数，即各坐标误差的最大值，不超过 0.01。PDDL 则比较逻辑等价，而不是逐字符匹配；作者在本数据集的有限目标范围内转成析取范式后比较。

[判断] 这些规则适合作为场景编译器的可测试协议：一端检查类型、ID 和单位，一端检查输出是否能解析以及引用是否存在。论文用提示示例约束格式，没有单独消融“相同信息换格式”，也没有证明提示约束能保证所有输出均合法。若要严格保证格式，需要额外的解析器、schema 校验或约束解码。

## 证据：哪个实验支撑哪个主张

小图为楼内一层，由 65 个物体、96 个二维位置、5 个区域组成；大图为公里级室外营地。两图均来自 Spot 机器人遥操作采集的 RGB-D 数据，经 Hydra 构建。每图各有 100 道问答题，指令集为小图 102 条、大图 82 条。模型温度设为 0，Qwen3-32B 用四位量化，在 RTX 4090 上经 Ollama 运行；实验直接调用预训练模型，无额外训练。

| 主张 | 支撑实验 | 怎么读 |
|---|---|---|
| 大图上按需查询比塞入整图更可靠 | 表I，GPT-4.1 大图问答：Cypher多轮 / 文本上下文 / Python多轮 = 77% / 33% / 32%；大图目标翻译为 56% / 41% / 51% | 同一模型、同一任务下的大图收益；问答比目标翻译的优势更明显 |
| 小图不一定需要复杂检索才能完成任务 | 表I，小图目标翻译：Cypher多轮和文本上下文均为 65% | 小图文字基线仍有竞争力，不能推广成“结构查询在所有条件都胜出” |
| 多轮反馈对Cypher有帮助，但不是任意工具的普遍规律 | 表I，大图目标翻译单轮Cypher 46%→多轮56%；Python单轮55%→多轮51% | 允许纠错提高上限，也可能引入错误，增益依赖接口与任务 |
| 返回少量结构数据大幅压缩模型输入 | 表IV，大图目标翻译平均初始输入/工具返回：Cypher 2,395 / 1,596 token；文字基线初始输入582,202 token | 按表中两项合计，3,991 对 582,202，约缩减146倍；不是端到端费用或耗时倍数 |
| 本地模型也能借助接口，但模型能力仍重要 | 表III，Qwen3-32B大图问答/目标翻译67%/55%；同接口Claude Opus 4.1为83%/80% | 本地部署可行；接口不消除推理能力差距 |

表IV 的输出也随工具使用增加：大图 Cypher 平均输出 942 token，而文字基线为 56。因此输入缩减不能直接当作总生成成本缩减。初始全属性图“约一千七百万 token”来自引言，表IV 的约五十八万来自 §V-A 筛选过字段的文字基线，两者是不同序列化口径。

## 局限与后续

准确率首先受地图和本体约束。图缺少某个物体，查询无法凭空找回；本体没有表达某种状态，输出也无法依靠查询获得它。论文指出，所有方法都仍会在跨层包含关系上出错，GPT-4.1 有时不使用已经提供的传递包含语法。把计算交给数据库改善了执行可靠性，如何提出正确查询仍由模型承担。

主要实验只覆盖一张室内图和一张室外图，以及为其编写、具有明确标准答案的问题。没有跨大量建筑、动态场景或多人交互的统计结果，也没有系统报告置信区间、同题多次运行方差、完整延迟或建库成本。Python 基线使用非为 LLM 优化的专用 API；Cypher 的优势同时包含语言熟悉度、文档长度和接口抽象程度，实验未逐项拆开。

目标翻译正确表示逻辑目标正确。§V-D 明确允许正确目标在当前规划域中没有可行计划，因此主表不是机器人完成任务的成功率。真实机器人演示展示了“问地图、纠正把包误标为自行车的类别、再取回包”的闭环，但没有多任务重复试验统计。

作者把动态本体描述列为后续问题：机器人运行时若增添新属性或概念，数据库 schema 与模型看到的说明必须同步。[判断] 进一步可把查询和图更新分开授权，给写入加版本、来源和可回滚记录，给读取加结果数量上限及执行预算，再测高密度地图上的尾部延迟。数据库能进行更新是表达能力，更新结果持续正确则需要额外验证。

## 批注

**易误读**

- 论文研究的是已有图的查询接口，不是从相机自动建立三维场景图；也没有比较图像提示和文字提示哪种更好。
- 结构化接口把关系遍历和数字计算外包给执行器，因此收益含有额外计算和任务相关取数。它不是把完全相同的信息单纯改排版的实验。
- 场景中的唯一 symbol 与跨时间的稳定 ID 是两层要求。P 与 p 的大小写在本文尤其重要，混用会改变节点层与意义。
- PDDL 目标的逻辑等价不保证动作可执行，也不完整编码任意时间顺序。原文对“先到A再到B”的处理依靠 visited 与 at 等谓词，不能据此宣称已解决一般时序规划。
- 附录把 SLDP 展开写成 Set、Line、Dictionary、Point，但其语法和实验实际包括 List；本文按语法解释类型，不把该拼写当成独立表示类别。

**与其他论文的关联**

- [SceneScript](../arxiv-2403.13064/README.md)：从已定位观测预测类型化场景程序，着重建立可解释几何；本文在已有图上按需查询，着重减轻下游上下文负担。两者可在显式ID、类型和解释器层面衔接，但没有现成联合性能结论。
- [Graph-of-Mark](../arxiv-2603.06663/README.md)：把估计出的空间关系用图像与文本提示注入多模态模型。它解决关系怎样呈现给模型，本文解决关系怎样检索和计算。应分别控制信息量、感知误差、执行器能力和最终呈现方式。
- [EmbodiedRAG](https://arxiv.org/abs/2410.23968) 是引言直接比较的相关路线，按任务检索三维场景图内容；本文强调声明式多跳关系和几何运算。主实验没有直接运行 EmbodiedRAG，对其不足的讨论属于方法分析而非同设置胜负结果。

**未核实 / 待验证**

- 未运行作者代码、数据库或真实机器人。唯一性约束、查询超时、写入安全、跨会话ID保持、错误回滚、动态本体同步和端到端成本仍需实验。
