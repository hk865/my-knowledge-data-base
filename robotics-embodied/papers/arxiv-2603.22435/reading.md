# CaP-X：怎样拆开接口、感知与 Agent 能力

论文卡（本地来源，未发布） · [官方原文](https://arxiv.org/abs/2603.22435v2) · [官方 PDF](https://arxiv.org/pdf/2603.22435v2)

## 它首先是一套分清能力来源的方法

CaP-X 把 code-as-policy 的环境接口、评测、运行时增强与训练放在一起。CaP-Gym 用有状态 REPL 执行模型生成的代码；CaP-Bench 比较不同感知信息、动作抽象和反馈；CaP-Agent0 在不改模型权重的情况下增强推理与技能复用；CaP-RL 则训练代码模型。四者不能混成一个“免训练 Agent”。（§2–5）

## “抬起红色方块”背后隐藏了多少工作

高层 API 可以直接返回候选抓取位姿，Agent 只需打开夹爪、移动、闭合、抬起。低层 API 则要求程序自行读取 RGB-D、分割红色方块、调用抓取规划、转换坐标系，再调用运动控制器。表面上都是一段 Python，但前者的工具已经替 Agent 完成大量工作。

基准因此设置 S1–S4 单轮与 M1–M4 多轮条件。S1 使用特权状态；其他条件改变真实感知模块、低层原语、调用示例与视觉反馈。多轮里一次代码执行可包含多次机器人动作，Agent 看 stdout、错误或视觉差分后继续写代码；同一试验内不会因失败自动重置。因此“多轮”与“多次重开任务”也不是同一预算。（§3）

## 为什么视觉不一定直接越多越好

CaP-Agent0 将前后视觉变化转换成任务相关文字，配合推理集成和从成功执行中整理的技能库。某些被测模型直接加入图像反而不如结构化文字反馈，这是该模型和接口下的观察，不能推广为机器人无需视觉。低层运动仍依赖规划器、IK 及碰撞处理。

核心受控分析是七类单臂/双臂任务，每类每 tier 100 次；发布平台包含更多任务，不能把平台总任务数当成每张实验表都已完整覆盖。真人参考程序也经过调试，不能忽略其开发成本。（§3、附录 K）

## 训练路线与本地启发

CaP-RL 用环境结果训练 coding LLM，训练采用 S1 特权 API；作者也报告 S2 噪声感知条件下的测试与真机迁移，不能说它只有 oracle 测试。应区分“训练时使用特权状态”和“部署时可通过感知接口工作”，迁移结果也不等于从纯 RGB-D 条件完成全部训练。CaP-Agent0 不更新模型权重的说法不适用于 CaP-RL，相关训练和接口成本都应单列。

对 RPent 最有用的借鉴是先固定“一个工具内部到底帮了多少忙”。比较 FSM、Agent 和生成程序时，要使用相同原语，且统计真实机器人步数、重试、token 和总时间。否则新模型可能只是在更强 API 上完成了更容易的任务。
