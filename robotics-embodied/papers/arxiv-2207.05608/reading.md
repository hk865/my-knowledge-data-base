## 从“执行过”到“观察到什么”

这篇工作把环境反馈接回语言模型的下一次规划。作者关心的不是模型能否讲出步骤，而是抓取失败、物体位置变化或原计划不可行时，规划器能否改变行动。方法把成功检测、场景描述，以及主动提问的回答写进同一语言上下文；冻结语言模型根据这些新信息重试或重新规划。（§3）

## 用一次空抓理解闭环

教学例子是“将杯子放进托盘”。模型先选抓取技能，底层策略执行。反馈如果只是“工具正常返回”，模型可能继续搬运空夹爪；若成功检测器返回抓取未成功，并且场景描述显示杯子仍在桌面，模型就可以再次抓取。若杯子不可见，它还可以主动请求额外场景信息。每轮输入增加的是外部观测证据，而不是单纯延长内部推理。

论文区分三类反馈：Success 表示当前技能是否达到目标；Passive Scene Description 自动给出对象或进度；Active Scene Description 在模型提出问题后才返回答案。后者可能来自 VQA，也可能来自人。回答本身并不保证正确，闭环质量依然受检测器影响。

## 冻结什么，谁提供真实世界能力

LLM 使用少样例提示，不新增任务微调；可调用的机器人技能已经预训练。视觉模型、成功检测器和操作策略是不同部件，不能把系统成败全部归因给语言模型。仿真可以用环境真值做成功检测，部分实验中的场景或问答反馈含人工/理想化信息；不能统一称为纯视觉、无人自主系统。（§4）

实验覆盖仿真桌面、真实桌面和真实厨房等不同系统，说明语言反馈组织方式可以迁移；并不意味着所有场景都用同一个检测器或相同信息预算。因此本笔记不把跨平台结果合并成一个“Agent 成功率”。

## 与后续工作的关系

相对 SayCan，它显式把执行结果变成下一次语言决策的输入。相对 Code as Policies，它主要研究如何选已有技能，并不以生成任意控制程序为主要贡献。后来的 verifier、恢复策略和记忆库，则继续追问反馈是否可靠、何时检查，以及历史应保存多久。

对现有工程，直接可复用的是反馈的语义分层：命令是否送达、局部抓取是否成立、最终任务是否完成分别记录。对照试验应让固定状态机和 Agent 看到相同证据，否则增加信息与改善决策会混在一起。这里是研究建议，本次未修改任何工具返回格式。
