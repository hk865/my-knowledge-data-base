## 把整段控制程序作为改进对象

Act-Observe-Rewrite（AOR）问的是：失败后能否直接修改控制器实现，而不只是换子任务、改一个参数或重新训练网络？系统在一回合结束后读取关键帧、奖励、阶段日志和当前源码，诊断错误，再生成新的 Python 控制器供下一回合执行。（§4）

## 两个时间尺度

教学例子是堆叠方块。快速循环用 RGB-D 经视觉处理得到特征，再由 `get_action(features)` 输出动作；程序内部可以有接近、夹取、抬升和放置等阶段。慢速循环发生在回合之间：若方块始终在夹爪旁边，Agent 结合图像与代码检查坐标变换或目标计算，再改写控制器。LLM 不承担每一步实时伺服。

作者实现包括 HSV 颜色分割等视觉处理、带 `reset()` 的控制器类、保存结果和关键帧的回合记忆，以及多模态 coding agent。代码经过编译检查和动作限幅，失败时可以回退到先前可工作的实现。这些工程约束是方法可运行的组成部分，并非靠自然语言反思替代底层控制。

## 证据为何要收窄

论文主要在三个 robosuite 操作任务上展示程序迭代，包含 Lift、PickPlace 与 Stack。它支持“小规模仿真中，根据执行证据修改控制器”的可行性，尚不足以证明真实机械臂上的广泛适应或优于训练式通用策略。论文自己的 Stack 剩余失败说明：能够说出夹爪碰撞原因，不等于能够找到有效修复。（§5–6）

所有模型权重保持不变，改变的是程序和上下文。但交互回合、环境重置以及 Agent 推理都有成本，不能把“无梯度”解释为没有学习预算。本次未确认独立官方代码仓库，保留可追溯原文而不链接未经确认的同名实现。

## 和 CaP 的差别应如何表述

部分后作把原始 CaP 简称为 one-shot。准确区别是：CaP 生成的程序可以读取反馈并循环；AOR 重点是利用回合结果改写这段程序。把前者说成必然开环，会错误抹掉它已有的反馈表达能力。

对本地工程，可以借鉴“失败证据对应到哪个程序或接口假设”的诊断方式。当前不应让 Agent 自动修改运行代码后马上用评估种子反复试到成功；应把开发用初态与冻结后评价分开，这样才知道改进是否迁移。
