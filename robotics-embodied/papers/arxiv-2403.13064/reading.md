# SceneScript：把三维重建输出改成可解释的场景程序

> 状态：技术精读 · ECCV 2024 正文与补充材料 · 未复现

## 一句话

SceneScript 的核心增量，是把已定位的图像或点云编码成场景特征，再逐个生成墙、门、窗、物体框和部件的类型化命令，由解释器把命令变回几何；新增表示能力主要通过扩展命令及其监督数据实现。

## 它要解决的问题

机器人走完一间屋子，SLAM 可以留下相机轨迹和点云，但“这些点是一面墙，那一块是门，门属于哪面墙”仍然需要解释。若下游要修改布局、生成碰撞几何或引用具体实体，直接消费数百万个三维点会把几何、语义和连接关系的恢复工作留给每个应用。

SceneScript 选择的目标是**参数化场景重建**：输出能由少量参数确定的场景元素，而非逐点保留外观。墙由底边端点与高度描述，门窗由中心、宽高和所属墙描述，家具先由有朝向的包围盒描述。解释器据此生成明确的几何。这与绘图中从像素转向矢量图形相似：几何更规整，修改一个参数就能改变一个实体。

论文主要用建筑布局估计和三维物体检测检验这种表示。前者要求恢复墙、门、窗；后者要求识别类别并定位物体三维包围盒。场景输入来自完整的第一人称巡视，而不是要求模型单凭一张普通照片恢复整栋楼。原文 §4.1 假设已知相机位姿，主要点云实验使用 Aria MPS 视觉惯性系统生成的半稠密点云，即在有足够图像梯度的位置恢复三维点。

## 核心想法

作者手工定义一门领域专用语言，即只表达特定场景元素、参数类型和引用关系的小语言。网络承担从观测预测程序的工作，解释器承担程序到几何的确定性转换。三者的职责分别是：**感知信息从哪里来，场景可表达什么，表达出来的参数如何执行。**

基础命令包括 make_wall、make_door、make_window、make_bbox。门窗带 wall0_id、wall1_id，可引用潜在的两面墙；物体框带 id、class、位置、绕重力轴的朝向和三轴尺寸。增加 make_prim 后，物体框可关联长方体或拉伸圆柱组成的部件。这样的接口既包含几何参数，又包含实体间的显式引用。

关键是把这种程序也变成“下一个 token 预测”。token 是模型一次预测的离散符号，既可以代表命令类型，也可以代表量化后的参数值。这里使用自定义词表，而非通用语言模型把文本拆成子词的分词器。输出字符串易读是表示层的性质，模型实际预测的是离散索引。

对场景编译器最有用的思想是**先定义下游可解释的中间表示，再训练感知端产生这个表示**。[判断] 图像、点云和语言描述可以成为不同输入前端，统一命令和引用关系成为中间层，几何渲染、查询和规划成为不同后端。原文实证覆盖观测到结构命令及命令解释为几何，更多后端是由这个接口推导出的工程用途。

## 机制

**1. 三种输入编码配置，采用相同的程序解码架构。**

点云分支将 XYZ 点按 5 cm 网格离散，用稀疏三维卷积压缩为 K×512 的场景特征，K 远小于原始点数。稀疏卷积只在有数据的网格位置计算。有效位置按三维坐标字典序排列，并附上坐标作为位置提示，最终变成解码器可交叉注意的特征序列。补充材料 §C 给出约 20M 参数的点云编码器和约 35M 参数的八层解码器。

图像与点云分支先把每个三维点投影回已定位关键帧，取对应像素的图像特征，跨视角平均后与 XYZ 拼接，再送入同类稀疏编码器。这样几何点携带了识别门窗等元素的视觉线索。纯图像分支则使用 RayTran 式双向图像—体素注意：图像块与其视线穿过的体素交互，逐层聚合多视角信息。三种配置改变的是信息提取方式，输出语言和解码器架构保持一致。

**2. 带边界的序列，带类型的参数。**

抽象序列为 START、PART、CMD、若干参数、PART、下一条命令、STOP。PART 标记一条子命令的边界；具体命令决定后续参数的数量与含义。浮点参数按 t=round(x/res) 量化，整数和布尔参数转成整数。对长度使用 res=0.05 m，就把连续回归变成有限分类。

**示例数值：从测量到几何。** 假设一面墙 id=7，底边从 (0,0,0) 到 (4,0,0)，高 2.8 m；一扇门 id=1000，宽度测得 0.93 m、高度 2.07 m，中心为 (1,0,1.035)。在 5 cm 量化下，门宽 token=round(0.93/0.05)=19，解释后宽 0.95 m；高度 token=41，解释后为 2.05 m，分别相差 2 cm。门命令引用墙 7，解释器便能在指定墙上构造门的开口。若再把 open_degree 从 0 改为 90，才额外表达“门开了多少”；宽高和墙引用本身没有包含门状态。

这个例子同时说明表示代价与精度上限：一条命令用几个参数表达完整构件，而厘米级量化与粗粒度构件共同约束几何细节。START 等符号以及实际词表索引需要编码器处理，示例中的数字仅说明参数量化。

**3. ID 提供引用，持久身份要由系统另管。**

论文中的 id 使同一次场景描述里的门、墙、物体框和部件能相互引用。例如 make_prim 的 bbox_id 指向所属物体框，prim_num 还可对应桌面等部件语义。§3.2 允许场景用不同命令顺序描述，这有利于把语言定义与某个固定输出槽位解耦。

[判断] 用于持续运行的场景编译器时，应再区分“本次程序中的局部 ID”与“跨时间的实体 ID”。重建第二遍后，墙仍是同一面墙需要数据关联、版本映射与删除语义来保证。论文没有测 ID 在不同巡视、不同采样或增量更新后的稳定性。附加 UUID、观测时间和置信度会增加接口能力，但也增加感知或匹配责任。

**4. 格式扩展同时改变监督目标。**

加入 make_bbox 后，训练对里增加物体框；加入 make_prim 后，训练对增加经 CAD 模型分解得到的部件。正文 §6 的部件实验只覆盖桌、椅、沙发。补充材料 §H 再用曲线墙控制点、组合墙块、门铰链与开启角、Blender 参数化桌模型展示扩展。其共同点是更新命令与训练数据，网络架构可以维持原样。

训练使用标准序列交叉熵 L=−Σ log pθ(t_i | t_<i,F)，F 是输入场景特征。也就是说，教师给出正确历史 token，模型学习预测下一个 token。ASE 数据包含 100k 合成训练场景与额外 1k 测试场景：先有布局和物体模型，再模拟巡视、渲染图像，最后从视频恢复并对齐点云。补充材料 §D 报告有效 batch 64、约三至四天训练，但未报告足以换算训练算力的 GPU 型号和数量。

[判断] 因此要隔离“新格式本身”和“新增信息”的作用，应让同一组已检测实体、参数和引用分别通过普通文本、类型化文本与图形显示交给同一后端。SceneScript 的主要实验比较编码器和重建方法，没有做这种同信息量的接口对照。

## 证据：哪个实验支撑哪个主张

布局实体距离先匹配同类元素的四个角点，再取匹配后最大的角点距离；F1@5 cm 要求这个距离过关，再综合查准率与查全率。Avg F1 是在多组距离阈值上计算 F1 再平均。它与物体检测按三维包围盒 IoU、即交集体积除并集体积设阈值的指标不同。

| 主张 | 支撑实验 | 怎么读 |
|---|---|---|
| 可用统一命令恢复细粒度建筑布局 | 正文表2，ASE：RoomFormer / 点云 / 图像提升点云的平均 F1@5 cm 为 0.139 / 0.848 / 0.903；Avg F1 为 0.464 / 0.784 / 0.801 | 布局优势强；所有方法在 ASE 训练，不能把差距单归因于字符串格式 |
| 几何与视觉有互补性 | 同表纯图像 F1@5 cm 为 0.661；提升图像特征后，窗 F1 从点云的 0.692 升至 0.806 | 视觉特征对窗等实体特别有帮助；不是“图像一定优于点云” |
| 扩展输出语言能支持检测，但非所有数据集最优 | 正文表3，IoU≥0.5 的 F1：ASE 中 SceneScript / ImVoxelNet 为 0.577 / 0.516；ScanNet 中 SceneScript / SoftGroup 为 0.406 / 0.573 | 竞争力取决于数据集；ScanNet 不能宣称全面领先 |
| 编码器也贡献性能，需避免把全收益归于解码语言 | 补充表3：ASE 的 3DETR 换稀疏卷积编码器后，F1@0.5 从 0.078 升至 0.191 | 作者说明该变体仅部分训练；这证明编码方式重要，不能据此严格分解架构贡献 |
| 扩展到曲面具有可行性 | 补充表6，专门合成的曲线墙试验几何 IoU 为 0.990 | 支持受控测试中的参数恢复，不等于真实复杂建筑曲面泛化 |

论文不为每个物体输出跨场景可比较的置信度，因此用 F1 而非直接报告自己的 mAP。平均精度依赖检测置信度排序；补充 §G.5 展示，同一检测集合若只能按场景内顺序排列，改变场景顺序就会改变 AP。这是评价输出接口与基线对齐时必须保留的口径。

## 局限与后续

命令集由人设计，决定模型能表达哪类实体以及精细到什么程度。重力对齐的墙和物体框适合室内布局，毫米级细节、非标准构件和高精细外观需要别的表示补充。可扩展性降低了修改网络的成本，仍保留命令设计、数据生成与再训练成本。

观测覆盖和高度噪声影响重建。补充 §F.3 展示未充分巡视导致遗漏，以及整体形状合理但 Z 高度偏移的失败；案例选自测试集按墙误差排序最差的十个场景。纯图像编码器随房间数增加而显著下降，作者推测与注意力沿射线跨墙关联被遮挡观测有关。这提示场景编译器需要保存可见性与观测来源，让“未观测”成为显式状态。

语言定义能容纳任意长度，实际解码器的最大序列长与词表大小均为 2048。大场景可用分区程序、局部更新或数据库存储承载，论文没有评估这些扩展。正文 §7 报告场景推理随规模约需 2–5 秒，适合人查看和补拍的交互节奏；这一数字没有构成传感器端、SLAM、建图与推理的逐帧实时延迟测量。

[判断] 后续最值得补的验证是：固定检测信息量的格式消融、跨巡视 ID 保持率、引用完整性与非法参数率、超长场景的分区一致性，以及命令修改是否改善真实规划任务。它们分别检验接口质量、身份管理、编译可靠性、规模扩展和下游效用。

## 批注

**易误读**

- “语言模型”指按 token 自回归生成的任务模型。这里约 35M 参数的解码器不等于直接调用通用聊天 LLM，也没有证明其已经具备开放问答能力。
- 命令格式不强制整个场景的唯一排列，不等于实际模型具有无限上下文；显式 id 也不等于跨会话稳定身份。
- “添加一个命令”需要相应训练标签和学习过程。部件、门状态和曲线示例不能读成零样本添加新 schema。
- 本文的图文融合发生在感知编码阶段；把同一场景图画给 VLM 或改成 JSON，是另一种下游接口问题。
- 官方代码 README 区分 ASE 模型和内部专有合成数据训练的模型，后者含非曼哈顿布局，并明确用于网站演示。网站视频的效果不能全部归因于公开 ASE 训练条件；README 对 ASE 框标注的缺失说明标注为截至 2024-09-17，不能无核查地当成当前数据集状态。

**与其他论文的关联**

- [Graph-of-Mark](../arxiv-2603.06663/README.md)：先估计对象关系，再把图与文字提示交给 VLM。SceneScript 学习把观测变成可解释场景程序；二者分别靠近感知编译与模型输入提示，可组成两段式系统，但没有联合实验证据。
- [Structured Interfaces](../arxiv-2510.16643/README.md)：把已有三维场景图存入数据库，让 LLM 用 Cypher 按需取数。SceneScript 更关注图从何来及几何怎样表达，后者更关注图大了以后怎样查。共同的工程启发是让符号引用与结构计算由显式接口承载。
- Pix2Seq 是正文 §2.2 直接指出的近邻：把检测改成 token 序列。SceneScript 的增量是三维整场景、高层参数化命令及扩展实体；这个历史联系来自作者相关工作，而非仅凭形式相似推断。
