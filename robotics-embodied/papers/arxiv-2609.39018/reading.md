## 一次模型决策应该控制多长一段动作

URAI 研究动作粒度：如果每次接近、闭合、抬升、转移都单独问 LLM，时间和 token 开销会很大；如果一开始把整项任务交给程序，又可能缺少任务级灵活判断。它让编程 Agent 制作完整运动工具，执行 Agent 在每次工具返回后重新看现场、决定下一项调用。（§3）

## 以抓取放置工具为例

编程阶段将接近、抓取、搬运、放置和撤离组织成带参数的程序，明确路径、朝向、速度、夹爪事件与终止条件。执行 Agent 根据相机和深度等观测确定对象与参数，一次调用运行整段局部运动。控制器本地执行后返回新观测和状态；若物体没有留在目标位置，模型再选择修正工具。

程序工具与 GUI/API 共用同一合同。模型权重不更新；工具代码和调用策略在开发中变化，经验证后冻结用于评估。工具制作包含执行反馈和人类指导，所以评估运行成本与工具开发成本须分开列，不能只统计后者已经做好的情况下调用多快。

## 作者比较了什么

仿真主比较是五项 RoboDojo 任务、四个执行 Agent，每任务五个 seed。URAI 相对直接末端控制的汇总成功率为 18.0% 到 53.0%；另一个同工具比较中，两种 Agent 每次调用后再决策为 56%，预先写程序为 24%。这些是不同汇总集合，不能混成同一组差值。（§5、表 1）

仿真时间与输出 token 包含失败回合；论文还展示七项 AgileX 双臂真机任务。部分真机效率对照来自其他机器人上的公开记录，平台和协议不完全一致，适合做机制线索，不适合当作严格配对速度优势。

## 与 CaP、RAX 的联系

CaP 的程序也可以含反馈；URAI 进一步固定了“完整工具结束后，把任务判断交回模型”的边界。RAX 则更强调把已探索的任务逻辑编译成可独立运行的程序。两者是性能与调用成本的不同取舍，不是一个已淘汰另一个。

对 RPent，可以比较短 VLA 调用、完整抓取宏和带检查的较长程序。必须统一总动作和恢复预算，并计入预先制作工具的成本。本次未核验到独立官方 URAI 代码发布入口，保留论文链接，不用第三方同名仓库充数。
