# 面向机器人导航 Agent 的工具接口与动态时空信息

## 从视频到可行动状态

本报告讨论一个具体问题：在算力有限、环境持续变化的机器人上，怎样把地图、位姿、动态对象和视觉证据交给大模型，让它能选择合适的导航策略，又不把实时避障与安全控制交给慢速推理。重点是数据组织、工具契约和可验证的系统分工，不是挑选一个名字最多的模型组合。

**核心结论：先让后端维护可计算的世界状态，再让 Agent 按需查询状态与视觉证据。** 不建议把全部点云、全部视频和完整历史反复放进上下文，也不建议把一段自然语言场景描述当作机器人真正的空间状态。Agent 负责理解任务、消除语义歧义、选择路线或观察策略；定位、几何计算、跟踪、局部规划和安全停机在独立快路径运行，不等待大模型。

面向现有定位、建图与导航底座，最小增量是在旁路增加“有时间和坐标的状态查询、事件增量、按需视觉回看、受控目标级执行”。这是一条未来增强路线，应先完成基础导航的独立验收，再验证新增接口。

报告截至 2026 年 10 月 24 日。文中使用四种标记：[事实] 表示标准或官方接口机制；[论文演示] 表示作者在特定实验条件下展示的能力；[判断] 表示根据证据作出的解释；[建议] 表示本报告提出、仍需实测的工程设计。所有接口名、数值示例与更新预算均是建议，不是已有机器人实测成绩或安全标准。

## 1 先分清模型看到的内容与机器人知道的状态

### 1.1 视频能够直接输入 但不是完整的四维世界

[事实] 多模态模型不只接收文字。视觉编码器可以把图片或视频帧变成模型内部的视觉表示，再与文本和时间信息共同处理。因此，“模型处理 token”不等于“必须先把视频翻译成文字”。token 是模型处理信息的内部单位，视觉 token 不必对应一个中文词。

[判断] 视频输入与四维状态是不同层次。本文的四维或 4D 指三维空间随时间变化，即位置与时间共同构成的状态。普通 RGB 视频提供随时间变化的二维投影；它不会自动给出米制深度、统一世界坐标、跨帧对象身份、速度和误差范围。相机移动也会让静态物体在图像上移动。要得到可用于路径和风险计算的量，需要深度或激光观测、位姿、标定、时间同步、跨帧关联和状态估计。

例如，“前面有人往左走”可以帮助理解场景，但不能直接回答这名行人是否会在 0.8 秒后进入机器人占据的区域。后一个问题至少需要双方位置与运动估计、机器人尺寸、可用观测的年龄，以及预测假设。模型可解释计算结果，不宜凭视频直觉给出可靠的米数、速度或碰撞时间。

### 1.2 三条必须守住的边界

- **空间估计不等于语言总结。** “门在走廊尽头”是语义关系；门在 map 坐标中的位置、通行宽度和定位误差是另外的数据。自然语言不能替代它们。
- **模型预测不等于真实观测。** 遮挡后预测行人仍在前进，可以作为风险假设，但不能更新“最后看见时间”，也不能伪装成新的测量。
- **工具接收不等于动作成功。** 导航请求被接受，只能说明任务已登记。到达、取消完成、阻塞和失败都必须由执行状态确认。

### 1.3 一个足够简单的分工

[建议] 系统可分为四层，不必为此先引入大型 Agent 框架。

1. **传感与实时层**：接收相机、激光、惯性数据；维护位姿、近场障碍和执行安全条件。
2. **状态层**：维护局部几何、对象轨迹、事件和证据索引，负责坐标变换、版本和过期判断。
3. **工具层**：把状态变成有边界的查询，把动作变成带前置检查的任务。
4. **Agent 层**：根据任务选择查询、路线或观察动作；收到新证据后修改高层计划。

状态层可先是一小组进程和普通数据结构，而不是完整“世界模型平台”。工具层尽量复用已有查询与导航接口，只加必要的信息转换，不重造一套复杂校验与安全引擎。关键是语义推理慢下来、超时或断网时，实时层仍能独立工作。Nav2 的 Collision Monitor 提供一个相关机制参考：它可直接依据传感数据执行减速或停止，不必等待常规规划链；官方同时明确说明这不构成硬实时安全认证。[Nav2 官方文档](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/collision_monitor/configuring_collision_monitor_node/)

## 2 五种输入路线怎样选择

[判断] 以下五条是工程输入路线，并非五种互斥模型。一个系统可以组合使用，但每条路线保留和丢失的信息不同。

| 输入路线 | 给模型什么 | 最适合解决什么 | 主要缺口 | 低算力使用方式 |
| --- | --- | --- | --- | --- |
| 结构化快照与查询结果 | 位姿、对象、局部地图摘要和风险字段 | 路线选择、条件判断、工具组合 | 依赖后端估计，摘要可能漏掉语义 | 默认入口，限制范围与条数 |
| 单帧与稀疏多帧 | 当前图像、历史关键帧、局部裁剪 | 识别物品、读标志、复核歧义 | 短事件缺失，跨帧身份不稳定 | 事件触发，给时间戳和证据 ID |
| 有限视频或在线视频会话 | 一段时间内的帧及时间信息 | 动作、先后关系、近期变化 | 抽帧与排队延迟，不保证度量运动 | 短窗口与硬预算，不无限续传 |
| 对象图与时序记忆 | 对象、关系、轨迹与变化记录 | 长任务查询、找物、过去状态回溯 | 关联与维护有成本，图也会错 | 任务相关子图，局部更新 |
| 按需混合输入 | 紧凑状态，加可回查图像或短片段 | 在预算内兼顾几何、语义和证据 | 接口设计与一致性要求更高 | 作为推荐目标，逐步增加能力 |

### 2.1 结构化输入的价值是可核查 不是把一切写成文字

结构化快照应表达“什么被测量、在何时、在哪个坐标系、误差多少”。它可以用 JSON 等机器可读格式，也可附一张局部俯视图。对象列表只返回与当前目标或空间窗口相关的部分；局部地图由工具查询，不必每次重新发送全图。

代价是后端必须真的具备这些估计能力。没有深度或可靠投影时，应返回位置未知，而不是让模型补齐坐标。结构化输入也不等于永远只用文本：看不清的门牌、特殊障碍和动作歧义仍应调取图像证据。

### 2.2 多帧适合复核 但时间间隔必须显式

连续附上几张图片，是一种容易实现的输入方式。每张图应带采集时间、相机标识和机器人位姿引用，必要时标注对象 ID。否则模型很容易把“机器人转头”与“对象移动”混在一起。

[事实] Qwen2.5-VL 官方示例支持图像列表和视频文件，并提供帧率与像素预算选项。有限多帧输入后生成回答，仍是一次有限请求；应用反复发送滑动窗口，不等于模型原生拥有无限持续记忆。[Qwen2.5-VL 官方代码](https://github.com/QwenLM-corp/Qwen2.5-VL/blob/main/README.md)

### 2.3 视频文件 在线会话与专用流式模型不是同一回事

[事实] 普通视频接口通常会解码并抽帧。Gemini 视频理解文档说明默认按 1 FPS 采样，并允许配置采样等选项；快速动作可能因采样而遗漏。持续在线会话则保留连接和对话状态，但其视觉输入能力也有明确限制。调研时 Gemini Live 文档给出的视觉输入是 JPEG、最高 1 FPS，不能据此宣称已经消费相机原始 30 FPS 的全部运动信息。[普通视频文档](https://ai.google.dev/gemini-api/docs/video-understanding)；[Live API 能力文档](https://ai.google.dev/gemini-api/docs/live-api/capabilities)

[论文演示] VideoLLM-online 针对视频流中的时序对齐与及时响应训练；论文在特定 A100、模型与视频条件下报告吞吐。Flash-VStream 把连续视觉编码和记忆维护，与异步问答分开。这些研究支持“持续感知、按需提问”的方向，但没有证明任意低功耗机器人能用视频模型承担高频闭环。[VideoLLM-online](https://openaccess.thecvf.com/content/CVPR2024/papers/Chen_VideoLLM-online_Online_Video_Large_Language_Model_for_Streaming_Video_CVPR_2024_paper.pdf)；[Flash-VStream](https://openaccess.thecvf.com/content/ICCV2025/papers/Zhang_Flash-VStream_Efficient_Real-Time_Understanding_for_Long_Video_Streams_ICCV_2025_paper.pdf)

另一个易混点是输出流式返回。API 中的 stream 选项常常只表示答案逐 token 返回，不表示摄像头输入会在推理期间持续更新。选择产品时要分别核对输入能否追加、上下文怎样保留、视频如何采样、答案能否取消，以及迟到结果怎样处理。

### 2.4 对象图保留关系 事件保留变化

场景图是把物体、房间或通道作为节点，把“位于、相邻、阻挡”等关系作为边的数据结构。它能让 Agent 只展开任务需要的区域，而不扫描整张地图。但图中的“行人阻挡通道”应带有效时间，不能永远保留为静态事实。

事件则记录变化，例如“行人进入通道”“目标失联”“门被移走”“重定位使地图坐标修正”。事件不替代当前状态：收到“通道恢复”后仍要查询新的局部风险；没收到事件也不等于没有危险。事件流必须报告丢失、截断或游标过期。

[建议] 低算力系统优先保留短时轨迹、必要事件和少量代表视图。先不追求所有对象、所有关系和永久历史的完整重建。

## 3 现有研究分别解决了哪一部分

### 3.1 从语言到技能 关键是可执行性而不是函数数量

[论文演示] SayCan 把语言任务相关性与技能可供性结合。可供性在这里指“当前条件下这个技能有没有机会完成”。它提示工具不能只写一句功能描述，还要检查前置条件。Code as Policies 展示语言模型组合感知和控制原语的能力，但生成程序本身不是安全证明。[SayCan](https://say-can.github.io/)；[Code as Policies](https://code-as-policies.github.io/)

[建议] 初期不必复制完整训练路线。可用已有规划器、规则和状态检查给出“可执行、阻塞、未知”及原因；只开放有限目标与技能，避免让模型直接发布裸速度、任意 ROS 话题、任意脚本或电机指令。

### 3.2 从大地图到任务相关子图

[论文演示] ConceptGraphs 从带位姿的 RGB-D 观测构建开放词汇对象表示及关系，可支持语言查询和规划。SayPlan 用层次三维场景图表达大环境，通过展开和收缩相关节点以及规划器反馈减少语言规划负担。前者不是移动物体长期身份与预测的完整解法；后者也不是人群中的实时避障系统。[ConceptGraphs](https://concept-graphs.github.io/)；[SayPlan](https://sayplan.github.io/)

[建议] 借鉴它们的数据选择机制，比直接搬入整套系统更适合早期实现：先查房间和通道，再查候选目标附近对象，最后只取有关图像。经典规划器连接语义目标，Agent 不逐点生成一条米制路径。

### 3.3 动态表示既包括运动 也包括环境长期变化

[论文演示] Khronos 构建时空度量语义地图，区分快速短期动态与较慢的长期环境变化。DovSG 演示局部更新对象图，以应对任务间物品被移动等变化。ST-OVSG 把时序匹配和延迟信息引入开放词汇三维场景表示。它们分别为动态状态、局部修订、时间与延迟建模提供参考，不能合并成“已证明四足自主动态导航安全”。[Khronos](https://github.com/MIT-SPARK/Khronos)；[DovSG](https://bjhyzj.github.io/dovsg-web/)；[ST-OVSG](https://arxiv.org/abs/2509.23107)

[判断] “支持动态”至少有三种含义：在线融合新帧、发现物品位置变化、追踪连续运动对象。看到其中一种能力，不能默认另外两种也已解决。选择实现时应先写清需要的是哪一种，以及它怎样进入规划与执行。

## 4 状态层应该保存什么

### 4.1 四类数据及其关系

[建议] 状态层至少保留以下四类数据，原始大数据留在后端。

- **几何与拓扑**：占据或距离表示、地面和坡度、房间与通道、局部地图块和版本。四足还需要可落足性等约束；“语义上像地面”不等于可靠可走。
- **对象轨迹**：对象 ID、生命周期、三维位置和尺寸、速度、误差、类别候选、最后真实观测时间。对象 ID 表示当前跟踪实例，不是人的真实身份。
- **事件与关系**：进入、离开、受阻、恢复、跟踪丢失、位置改变和重定位；关系注明开始、结束或最后确认时间。
- **证据索引**：传感帧、对象裁剪、视频片段和估计来源的引用。状态返回引用，只有需要时才取图像或短片段。

视觉证据与状态应能双向定位：从对象查到当时的帧，从帧查到相关对象与估计版本。环形缓存覆盖旧视频后，证据接口应明确返回已过期，不能再生成一段看似原始的回放。

### 4.2 最小字段与可选增强分开

[建议] 第一版最少把时间、坐标、对象 ID 和任务状态说清楚；证据能查到来源，误差与缺测不被隐藏。不要一开始就把所有版本号、事务字段和校验链做成调用门槛。下表是信息需求清单，不是要求每次响应携带全部字段。

| 字段组 | 最少内容 | 防止的错误 |
| --- | --- | --- |
| 时间域 | 观测时间；多时钟或仿真重置时加 clock_domain、time_epoch | 仿真重置后误用旧目标；混用墙钟与仿真时间 |
| 观测与处理时间 | last_seen_stamp、processed_stamp、as_of | 把刚算完的旧画面当成当前世界 |
| 新鲜度 | 各对象最后观测时间；按需求加 age_ms 或有效期 | 总体快照新，但某个对象实际已失联 |
| 坐标与单位 | frame_id、米、秒、速度定义 | 混用相机、机体与地图坐标 |
| 可选版本 | 有需要时加 snapshot_id、map_revision 或变换版本 | 回环或重定位后继续用旧全局位置 |
| 来源 | evidence_ids、estimator、observation_kind | 把预测、推断或真值误当传感测量 |

[事实] ROS REP 105 区分 map 与 odom：map 适合作长期全局参照，但定位修正可能引起跳变；odom 连续，但会积累漂移。因此全局语义目标与短时连续控制不应不加区分地共用旧坐标。[REP 105 官方源码](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)

[建议] 变换必须查询观测发生时刻，而不是随手取最新变换。地图修正后重新验证相关目标和计划，不必因为任意地图块更新就中止所有任务。Gazebo 使用仿真时钟时，重置应切换 time_epoch，使上一次运行的状态、事件游标和动作凭据失效。传感时间与处理时间分开，跨机器年龄需要时钟同步或明确的误差界。

### 4.3 不要用一个置信度包办所有不确定性

检测类别分数、跨帧关联分数、位置协方差、预测分布与语言推断可信度不是同一个量。协方差表示状态误差的统计结构；未校准的分类分数不自动表示真实正确概率，视觉特征相似度也不是概率。

[建议] 返回分数类型、原始值与校准状态；位置和速度分别给误差。对象状态区分 observed、occluded、lost 等观测情况；预测单独带起点、预测时域、模型版本和不确定性。unknown 应与 free、occupied 明确分开，缺测不返回零速度或“安全”。短时碰撞时间 TTC 应由几何和运动模块按明确假设计算，并允许“不可可靠估计”。

## 5 八个工具足够建立第一版闭环

[建议] 下列接口是一组可实现的起点，不是要求采用某个协议或 Agent 框架。工具的价值来自输入输出与执行契约，HTTP、进程间调用或 ROS 封装只是承载方式。

### 5.1 公共契约保持轻量

第一版只读请求只需明确要查什么、查哪个范围、最多返回多少；结果说明观测时间、坐标、对象 ID、来源和是否缺测。时间窗口、最大年龄、快照引用和分页游标按工具需要添加。多个结果来自不同时刻时，说明时间差即可；不必为了向模型回答一个简单问题，先实现复杂的全局原子快照。

动作接口优先复用已有导航目标、状态与取消能力。工具适配层只做必要参数检查和执行前状态确认，实际可行性与安全由既有导航负责。需要网络重试时再加幂等键，防止同一请求启动两个任务；有异步延迟或坐标修正风险时再加版本和有效性条件。预算不足或证据缺失时返回可处理的错误，优先补查、等待或局部重规划，不把暂时陈旧升级成永久任务失败。

### 5.2 get_world_snapshot 获取最小世界快照

输入当前任务、查询半径或区域、所需字段与 max_age_ms；返回机器人位姿、定位健康度、相关对象、当前任务和状态引用。默认只给必要摘要，不附全图和所有图像。若关键定位或坐标不可用，返回 LOCALIZATION_UNCERTAIN 或 FRAME_UNAVAILABLE。它回答“我现在依据什么做决定”，不代替详细对象查询。

### 5.3 query_local_map 获取局部地图与变化

输入区域、分辨率、地图类型和已知 revision；返回局部地图、风险摘要或自该版本以来的增量。未变化时只返回 unchanged，过旧版本则明确要求重新取局部块。通行宽度等数值由几何模块计算。不能把“当前地图没有障碍”解释成“未观测空间没有障碍”。

### 5.4 query_objects 查询对象和短时轨迹

输入类别或对象 ID、空间/时间窗口、数量上限；返回三维状态、真实观测历史、关联质量和单独标记的预测。查询“门口那个人”时可以先给候选，不强行合成唯一 ID。失联、身份切换与遮挡要显式返回。对象是否阻挡路线由几何关系模块判断，不靠名称猜测。

### 5.5 get_evidence 按需取视觉证据

输入 evidence_id，或对象加时间区间；返回有限关键帧、裁剪或短片段，附采样间隔、采集时间和相机标识。设像素、帧数、时长上限；缺证据返回 EVIDENCE_EXPIRED。请求较高细节前先说明需要核实什么，例如“门是否真被关上”，不要每次把整个缓存交给模型。

### 5.6 evaluate_routes 计算候选路线与可行性

输入目标、快照、机器人约束和有限路线候选；由现有规划器返回距离、代价、最小间隙、动态冲突及失败原因。对比项必须给计量依据，不把未校准分数包装成成功概率。返回可执行、阻塞或未知；“未知”可以引导到安全观察点或等待新观测。

### 5.7 start_navigation 启动有边界的目标任务

输入明确世界目标、已验证对象目标或安全观察点；第一版只需目标、坐标与返回 task_id。速度配置可复用导航已有档位，不让模型任意输出速度。只有在确有需要时，才增加状态新鲜度、地图条件、超时与幂等键。适配层确认目标仍可解释，由既有导航做定位、变换与局部碰撞等必要检查；不为 Agent 另建重复检查链。观察动作可作为受限任务模式，不必另造一整套控制入口。

### 5.8 read_events 读取变化和任务进度

输入事件游标、感兴趣区域或 task_id；返回有序事件、任务反馈、最终结果和下个游标。可以长轮询或订阅，但必须限制等待时间和缓存规模。区分 accepted、running、blocked、canceling、succeeded、failed、canceled；游标过期时返回 CURSOR_EXPIRED 并要求补查最新快照。事件与任务状态读取在同一接口中表达，不让 Agent 为等结果不断重复发起动作。

### 5.9 cancel_navigation 取消指定任务

输入 task_id 和原因；返回取消请求是否被接受。只有最终 canceled 或其他终态才能确认结束，canceling 不是已经停稳。重复取消不应造成新副作用。物理急停与安全停机仍在独立实时机制中；不能因为大模型没有调用这个工具就继续危险动作。

[事实] ROS 2 Actions 的目标、反馈、结果与取消机制，提供了可参考的长任务语义。具体服务器怎样接受新目标、拒绝或抢占，仍由实现定义，不能默认“发新目标就自动安全停止旧目标”。本报告的 blocked、业务错误及幂等规则是其上层约定，不是原生状态的逐字复刻。[ROS 2 Actions 设计](https://design.ros2.org/articles/actions.html)

## 6 动态行人场景的完整信息链

场景是机器人前往门口，行人横穿前方窄通道。目标不是让模型对视频说得更生动，而是验证它是否在合适证据下选择正确策略，并且没有拖慢避障。

1. **采集与几何更新**。相机帧、深度或激光与位姿按时间对齐。近场保护持续运行。行人进入危险区域时，即使 Agent 正在推理，底层也必须按既有规则减速或停下。
2. **检测与关联**。检测器给出人像候选；跟踪器赋予 person_12，并利用深度或激光得到世界位置。不能只从像素位移推导世界速度。检测、关联与几何误差分别保留。
3. **生成状态与事件**。状态层更新真实观测时间和短时轨迹，形成 corridor_blocked 事件，附对象、空间、时间和证据引用。预测模块可估计短时运动走廊，但另外标明预测来源与有效期。
4. **唤醒语义决策**。Agent 收到事件与任务相关快照。它可先查 evaluate_routes：原通道冲突，B 通道较长但可行，或当前信息不足。距离和间隙由规划器提供。
5. **补证而非猜测**。如果问题是“行人是否在原地等待”，请求最近短片段；如果问题是“另一边能不能通过”，请求局部几何或安全观察点。视频解释与几何答案各司其职。
6. **选择高层策略**。Agent 在等待、重观察、绕行之间选择。它不因为“看起来人已经过去了”直接解除底层保护，也不输出步态或瞬时速度。
7. **执行前复核**。start_navigation 使用当前可解释的目标，由既有导航检查。期间若行人失联、通道再受阻或地图修正，导航按已有机制减速、等待、核对坐标或重规划；确实无法继续才结束任务，不把每次状态更新都变成取消条件。
8. **确认结果与保存证据**。到达由终态和到达判据确认。记录决策当时可见信息、调用与结果，方便区分感知错误、信息过期、策略错误或执行失败。

[建议] 若行人短时被遮挡，继续把“预测可能占据区域”交给局部风险处理，同时把对象标为 occluded；不要发送“行人已离开”事件来压缩不确定性。只有获得新证据或满足事先验证的遗忘规则，才能改变该判断。

## 7 更新率与延迟怎样定预算

### 7.1 以下是起始设计范围 不是性能基准

[建议] 优先继承候选底座已稳定达到的频率，不为整齐数字降低安全链能力。下表只给低速仿真原型的试验起点；真实可用频率取决于硬件、传感器、机器人速度和环境风险。所有频率都应测最坏负载下的实际周期，而不只是设置值。

| 路径 | 起始试验预算 | 设计原则 |
| --- | --- | --- |
| 近场保护与控制 | 继承底层已验证周期 | 不等待 Agent，不据本表宣称安全 |
| 位姿与局部几何发布 | 20–50 Hz 或底座实际频率 | 保留原始时间，监控跳变与丢帧 |
| 关键动态对象跟踪 | 5–15 Hz | 轻量快路径，误差与丢失显式化 |
| Agent 用状态快照 | 按需，或 1–5 Hz 缓存 | 不是每次更新都调用模型 |
| 重语义更新 | 事件触发，必要时 0.2–1 Hz | 排队有界，迟到可丢弃 |
| Agent 高层决策 | 事件或任务触发 | 超时不阻塞控制，限制工具回合 |
| 视觉证据缓存 | 例如最近 10–30 秒 | 容量硬上限，按需取短片段 |

这里的 5–15 Hz 跟踪和 20–50 Hz 几何只是资源分配假设，不能当作最低安全要求。若目标硬件达不到，应减小空间窗口、类别集合或重语义负担，再重新评估；不能靠把 Agent 调用调得更勤补偿感知缺口。

### 7.2 用观测年龄衡量实时性

端到端年龄至少包含采集、同步、预处理、队列、视觉编码、模型推理、工具往返和执行前等待。高 token 吞吐只覆盖其中一部分。应记录从传感采集到动作提交时的年龄，以及 P50、P95、P99 延迟；这些分位数分别描述典型与尾部情况。仿真时间用于物理状态，墙钟或单调时间用于计算延迟，两者不能混算。

[建议] 可先为只读快照设百毫秒级目标，为语义建议设秒级目标，但它们必须与速度、误差和通道余量一起验证。例如相对速度 1 m/s 时，额外 0.5 秒陈旧就对应约 0.5 米的运动距离；这只是运动学量级说明，不是碰撞模型或安全距离公式。实际还要加制动距离、感知和控制误差。

### 7.3 队列不允许无限积压

背压指处理跟不上输入时，限制上游继续堆数据。[建议] 对当前状态采用“保留最新”，对关键事件采用“有限保存并报告缺口”，对原始视频采用“环形覆盖”。同一对象的重复语义请求可合并；新的危险事件可以使旧推理结果失效。达到帧数、像素或时间预算时，优先保留变化前后与任务相关证据，而不是无条件均匀加长上下文。

取消模型请求只是省资源的手段，不能保证计算已停止。迟到结果到达时仍要检查快照、任务与时间域，失效就不执行。这比假设所有 API 都能即时中断更可靠。

## 8 低算力最小可行方案分四阶段做

### 阶段 A 只读旁路与可回放数据

[建议] 订阅现有位姿、局部地图、导航状态和稀疏图像，先实现快照、事件读取与证据接口。Agent 只解释、提出候选目标和标注缺证，不发控制。验收重点是时间、坐标、缺测、任务状态与观测年龄能否追溯；不先堆叠版本、哈希或复杂事务机制。原导航是独立基线，报告不把候选底座当作已验收结果。

### 阶段 B 小范围对象轨迹与事件

[建议] 先支持人、门、明显障碍等任务相关类别，采用设备能承受的检测与轻量跟踪；用可用深度或激光投影建立短时三维轨迹。先把误差、遮挡与身份切换处理正确，再增加开放词汇识别。Gazebo 真值只能进入评测支路，不能混进正式感知响应冒充系统能力。

### 阶段 C 低频语义和按需回看

[建议] 对新对象、低置信类别、显著变化或用户任务才调用较重视觉模型。复用对象描述，按区域和时间更新，避免每帧分割、每帧全图重建。Qwen3-VL 官方仓库包含小参数规格与时间对齐设计，可作为本地候选；“存在小模型”并不意味着目标设备一定实时，量化、分辨率、帧数与上下文都须实测。[Qwen3-VL 官方仓库](https://github.com/QwenLM/Qwen3-VL)

### 阶段 D 受控目标级导航

[建议] 在基础导航独立验收后，先开放已知静态目标、低速、限定地图的仿真导航，再加入动态行人场景。验收执行前校验、幂等、取消、终态、超时和故障降级。只有简单方案确实被数据证明确有瓶颈，才评估更完整的时空建图或专门流式模型。

每阶段只加一个主要能力，保持可回退。CPU、GPU、内存、带宽、功耗和温度同时记录。粗体素、低分辨率和局部窗口可节省算力，但窄通道必须保留足够几何精度；被压缩掉的安全信息不能用自然语言警告补回来。

## 9 怎样证明接口确实提高能力

### 9.1 先固定基线 再分离收益来源

[建议] 在相同地图、传感流、机器人速度和算力限制下比较：

1. 原导航，无 Agent。
2. Agent 只看单帧与任务文本。
3. Agent 只看结构化快照。
4. Agent 看快照、短时轨迹与事件。
5. 在第 4 组上增加按需视觉证据。
6. 在预算允许时，对照持续视频或专门视频模型。

先做同一录制数据的因果回放，只给当时已产生的信息，再做闭环仿真。离线对同一录像回答，不会因路线选择改变后续观测；闭环会改变。因此两者都要做，不能把回放问答提高直接称为导航成功率提高。不要让模型看到未来帧、事后修正轨迹或用于评分的真值。

### 9.2 指标按失败链分层

| 层次 | 必须记录的指标 | 回答的问题 |
| --- | --- | --- |
| 感知与跟踪 | 三维位置/速度误差、身份切换、遮挡误关联 | 状态是否可信 |
| 动态变化 | 短事件漏检、事件延迟、变化恢复时间 | 变化是否及时进入接口 |
| 时间一致性 | 观测年龄、P95/P99、跨源时间差 | 模型读到的是不是旧世界 |
| 工具可靠性 | 合法参数率、无效 ID、过期拒绝、重试重复任务数 | 接口是否真正可用 |
| 执行与安全 | 取消完成、终态准确、碰撞/近碰、保护触发 | 动作是否安全闭环 |
| Agent 任务 | 成功率、绕行代价、观察次数、恢复率 | 高层决策是否有用 |
| 资源 | CPU/GPU、内存、帧/像素/token、能耗 | 收益能否在设备上承担 |

近碰阈值、到达判据与安全条件要事先规定，并报告场景数、随机种子、置信区间和失败案例。不要只放成功片段，也不要只报告平均延迟。只读 Agent 的不安全建议与实际碰撞分开计分，避免底层保护掩盖上层错误。

### 9.3 三组关键消融

消融指有控制地移除一个组件，观察性能怎样改变。[建议] 优先做三组，而不是一次比较十个框架。

- **信息结构消融**：去掉对象 ID、时间戳、误差或事件，分别看身份混淆、过期计划与误判是否增加。安全校验始终保留；移除校验只可在隔离仿真中研究，不能进入真实机器人。
- **证据获取消融**：固定关键帧、均匀短视频与事件触发回看，在相同图像预算下比较。看额外证据是否真的降低失败，而不只是增加推理时间。
- **记忆与资源消融**：全量历史对比有限轨迹/事件，低中高分辨率对比；寻找收益拐点，同时检查窄通道与短事件是否受损。

故障注入至少覆盖相机延迟、缺深度、对象被遮挡、ID 切换、门口目标搬走、地图坐标修正、仿真时钟重置、模型超时和事件缓存溢出。预期结果应写成可检验行为，例如“拒绝旧 epoch 动作”“取消后不再推进”，而不是笼统的“更鲁棒”。

### 9.4 视频问答基准只能补充 不能替代机器人验收

[论文演示] StreamingBench 在不同时间点提问，覆盖即时视觉、跨模态与历史信息；OVO-Bench 区分回顾过去、理解当前、等待未来证据等在线任务。它们适合检查视频模型是否利用正确的时间证据，但问答正确率不包含机器人制动、可通行几何和任务取消。[StreamingBench](https://streamingbench.github.io/)；[OVO-Bench](https://arxiv.org/abs/2501.05510)

[建议] 可借用这些时间因果测试方式，再增加机器人状态、工具与闭环安全指标。回答“那个人接下来去哪”与在不确定条件下选择“暂时不要通过”是两个不同能力。

## 10 局限和下一步决策

### 10.1 仍然没有被接口自动解决的问题

- **感知上限**：遮挡、透明或反光物体、深度缺失和标定误差仍会影响状态；格式正确不等于数据真实。
- **身份连续性**：普通跟踪 ID 可能断裂，不应把重现对象当作同一人的可靠身份识别。
- **预测多样性**：行人会停下、转向或避让。单条预测线只是一个假设，越远期越不确定。
- **四足约束**：身体通过并不意味着可靠落足；楼梯、坡度、地面性质与机体姿态需要对应模块。
- **长任务记忆**：事件压缩可能漏掉关键原因，原始证据也会过期。必须允许“不知道”与重新观察。
- **模型与服务变化**：API 的抽帧、会话和模型规格会更新。部署时固定版本、复查限制，不把云端演示视为设备能力。
- **安全保证**：本报告没有给出任何安全认证或真实硬件实时保证，仍需系统级风险分析和独立验收。

### 10.2 建议现在决定的四件事

1. 先定义一个窄任务：已知地图中前往目标门，期间允许行人横穿。
2. 固定第一版最小状态契约：时间、坐标、对象 ID、任务状态清楚，误差和证据可追溯；其他字段按实际风险增加。
3. 先完成只读旁路与回放验收，再增加受控执行，保持原导航闭环独立。
4. 把“在相同资源预算下减少错误或恢复失败”作为目标，不以传入更多数据、模型更大或工具更多作为成功指标。

**最终取舍：** 对低算力导航，最先值得建设的是有限、可查询、可追溯的动态状态，以及能在执行前补查陈旧信息的轻量工具适配。视频应作为丰富但有预算的证据源；对象轨迹和局部几何提供可计算状态；Agent 在这些信息之上选择策略。这样既能发挥大模型的语义能力，也保留机器人对时间、空间和执行结果的要求，不让新增架构反过来压垮已有导航。

## 批注

**参考文献与阅读路线**

建议先读 1–4 理解工具与执行，再读 5–9 理解空间记忆，最后读 10–17 选择视频路线与评测。文档类来源按调研时版本使用；项目页与论文只证明各自条件下的能力，不意味着系统可直接兼容或达到同样实时性。

1. **SayCan**，2022。先看语言相关性与技能可执行性怎样结合，理解为何动作前置检查不可缺。项目与论文：[项目](https://say-can.github.io/)；[论文](https://arxiv.org/abs/2204.01691)。
2. **Code as Policies**，2022。看高层语言怎样组合低层原语；不要把程序生成能力当成任意代码安全执行许可。[项目](https://code-as-policies.github.io/)；[论文](https://arxiv.org/abs/2209.07753)。
3. **ROS 2 Actions**，2019–2020 设计文档。用于目标、反馈、结果与取消语义；上层仍需定义超时、重试和业务状态。[官方设计](https://design.ros2.org/articles/actions.html)。
4. **Nav2 Collision Monitor**，官方文档。用于理解独立近场保护的分工，同时阅读其非硬实时安全认证的限制。[官方文档](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/collision_monitor/configuring_collision_monitor_node/)。
5. **ConceptGraphs**，2023 预印本、ICRA 2024。对象中心开放词汇三维表示的起点；重点看多视角关联，不预设动态预测能力。[项目](https://concept-graphs.github.io/)；[论文](https://arxiv.org/abs/2309.16650)。
6. **SayPlan**，CoRL 2023。最值得借鉴的是层次子图查询、经典规划与反馈修正，而非一次把全部场景传给 LLM。[项目](https://sayplan.github.io/)；[正式论文](https://proceedings.mlr.press/v229/rana23a.html)。
7. **Khronos**，RSS 2024。阅读快慢变化分离与时空度量语义地图；完整系统集成和版本依赖需单独评估。[论文](https://arxiv.org/abs/2402.13817)；[官方代码](https://github.com/MIT-SPARK/Khronos)。
8. **DovSG**，2024 预印本。阅读对象变化后的局部图更新；不要将任务间物品变化直接等同于高速行人避障。[项目](https://bjhyzj.github.io/dovsg-web/)；[论文](https://arxiv.org/abs/2410.11989)。
9. **ST-OVSG**，2025 预印本。用于思考时间、延迟与任务相关过滤；遥操作规划结果不直接证明自主导航安全。[论文](https://arxiv.org/abs/2509.23107)。
10. **Qwen2.5-VL**，官方代码。核查多图、视频文件、帧率与像素预算的实际输入方式。[README](https://github.com/QwenLM-corp/Qwen2.5-VL/blob/main/README.md)。
11. **Gemini Video Understanding**，官方文档。核查有限视频输入、默认采样和快速事件遗漏，不把视频文件接口理解成全帧实时传感器。[官方文档](https://ai.google.dev/gemini-api/docs/video-understanding)。
12. **Gemini Live API**，官方文档。核查在线会话与图像输入限制，分别考虑连接、上下文与视觉采样。[概览](https://ai.google.dev/gemini-api/docs/live-api)；[能力与限制](https://ai.google.dev/gemini-api/docs/live-api/capabilities)。
13. **VideoLLM-online**，CVPR 2024。用于理解专门的在线时序训练与响应；实测吞吐受硬件、模型和片段条件限制。[正式论文](https://openaccess.thecvf.com/content/CVPR2024/papers/Chen_VideoLLM-online_Online_Video_Large_Language_Model_for_Streaming_Video_CVPR_2024_paper.pdf)。
14. **Flash-VStream**，ICCV 2025。用于理解持续帧编码、压缩记忆和异步问答的分离。[正式论文](https://openaccess.thecvf.com/content/ICCV2025/papers/Zhang_Flash-VStream_Efficient_Real-Time_Understanding_for_Long_Video_Streams_ICCV_2025_paper.pdf)；[官方代码](https://github.com/IVGSZ/Flash-VStream)。
15. **Qwen3-VL**，官方代码。作为小模型与时间对齐的候选入口；先做目标设备测试，不按参数量推定实时性。[官方仓库](https://github.com/QwenLM/Qwen3-VL)。
16. **StreamingBench**。用于检查不同时间点的在线视频问答与历史信息使用，不替代机器人安全指标。[官方基准](https://streamingbench.github.io/)。
17. **OVO-Bench**，CVPR 2025。用于检查回溯、当前与未来证据的不同要求，以及回答时机。[论文](https://arxiv.org/abs/2501.05510)。
18. **ROS REP 105**，2010。实施前核对 map、odom、base_link 的含义与变换责任。[官方源码](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)。

边界说明：本报告提出的接口、预算和阶段验收均为工程建议，不是上述来源共同实现的一套现成产品。没有将不同论文的能力、不同硬件的帧率或后续版本的接口拼接为已验证系统。
