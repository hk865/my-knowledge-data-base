# Agent 记忆：历史怎样回到新任务里

## 我的问题

2026 年 10 月 5 日的问题是：一个 Agent 除了当前环境，还需要哪些历史状态与经过核实的事实？把场景换成安全测试、调用工具找 Bug、大型系统维护和从零开发，能否形成共同的记忆规范？

进一步的问题落在已有的架构图与任务图上：怎样把可复用的历史留在局部节点或结构中，使新任务自然找到相关信息？这里关心的是历史与当前对象之间的联系，而不只是把文字变成结构化字段。

## 目前的判断

- [建议] 把“事实的原始证据”“从证据得到的解释”“解释在什么版本和条件下适用”分开。图用于找到相关对象，历史记录提供依据，新任务仍要检查适用条件。
- [建议] 在一个修复案例中检验最小闭环：旧测试失败被记录，下一次修改能找到它，读取者检查代码版本并重跑相关验证，再决定保留、替代或作废旧结论。这个流程是阅读材料后的教学建议，尚未成为已采纳的项目方案。
- [建议] 将任务内的上下文压缩、跨会话的经验保存和组件的启停管理分开比较。SWE-MeM、PROJECTMEM 与 Cordis 分别提供不同层面的参照，不能仅因都涉及“状态”就当作同一种记忆机制。

## 四类场景要保留什么线索

安全测试需要把观察、测试环境和授权范围连在一起；工具式排错需要保留复现条件、失败尝试及验证输出；大型系统维护要知道一个结论属于哪个模块、版本和依赖边界；从零开发首先积累的是需求约束、设计取舍和第一批测试，而不是凭空获得过去的失败经验。这是比较阅读的起点，具体字段和保留策略仍需用实际任务验证。

## 待验证

- 历史信息被正确检索出来以后，是否真的减少重复失败，还是只增加上下文长度？
- 依赖或代码版本变化时，哪些事实可以继续用，哪些必须重新验证？
- 多个任务共享记忆时，怎样处理相互冲突的观察、权限不同的证据和并发更新？
- 评估是否固定模型、工具、预算和任务历史，避免把系统配置差异误记为记忆方法收益？
