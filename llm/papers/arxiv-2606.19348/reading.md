# DeepSeek-V4：KV 先沿序列压缩再稀疏读取，让 1M 上下文成为常规配置

> 状态：技术精读 · 原文 arXiv:2606.19348v1（预览版）· 未复现

## 一句话

DeepSeek-AI（2026 年 4 月）把注意力从 V3.2 的"MLA 加 DSA 选 token"改成两种压缩注意力交错：CSA 把每 4 个 token 的 KV 压成一条再稀疏选读，HCA 把每 128 个 token 压成一条后稠密读全；残差连接换成 mHC（把残差流加宽成多条并约束层间混合矩阵），优化器换成 Muon（对梯度动量矩阵做近似正交化后再更新），DeepSeekMoE 与 MTP（多 token 预测：每个位置额外预测再下一个 token）基本不变。V4-Pro 1.6T 总参数、每 token 激活 49B，V4-Flash 284B、激活 13B，都支持 1M token 上下文；在 1M 长度下，V4-Pro 每生成一个 token 的计算量约为 V3.2 的 27%，KV 缓存约为 10%。

## 它要解决的问题

推理模型靠更长的思考提升能力（测试时扩展），智能体任务又要在上下文里攒下大量工具调用的历史；作者在引言里把原始注意力随长度平方增长的计算列为这两条路的共同瓶颈（§1）。

到 V3.2 为止，DeepSeek 在两件事上各走了一步：

- **每个位置存得少。** [DeepSeek-V2](../deepseek-v2/reading.md) 的 MLA（多头潜在注意力，一句话：每层每个历史 token 只缓存一个 512 维潜向量加一个 64 维位置键）把 KV 压到 576 个数，[V3](../arxiv-2412.19437/README.md) 原样沿用。
- **每次读得少。** [V3.2](../arxiv-2512.02556/README.md) 的 DSA（DeepSeek 稀疏注意力，一句话：一个很小的"闪电索引器"给所有历史 token 打分，主注意力只读得分最高的 2048 个）把主注意力从 O(L²) 降到 O(Lk)，思路来自 [NSA](../arxiv-2502.11089/README.md)。

留下的问题是：历史位置的条数一条没少。缓存仍随长度线性增长，索引器仍要给每个历史 token 打分；V3.2 的上下文上限是 128K，原文自述 20% 以上的搜索智能体测试因此超长。V4 要回答：能否让 1M 上下文的显存与单步计算都降到"日常可用"的量级。

## 核心想法

**增量集中在注意力：在"每个位置存得少""每次读得少"之外，加上"位置条数变少"——沿序列把相邻 token 的 KV 合成一条。** 其余改动是配套的：mHC 用于加深加宽的稳定性，Muon 用于更快收敛，滑窗分支和 sink 修补压缩带来的局部信息损失。

相对前两代，部件变化如下（V4 一栏取自原文 §2、§4.2，V3、V3.2 两栏取自各自的报告）：

| 部件 | V3（2024-12） | V3.2（2025-12） | V4（2026-04） |

| 单条 KV 的存储 | 576 维潜向量 | 同左，部署时 FP8 | 512 维，448 维 FP8 + 64 维 RoPE 用 BF16；索引器打分在 FP4 下算 |
| 上下文上限 | 128K | 128K | 1M |

## 机制

### 1 CSA：每 4 个 token 压成一条，再挑 top-k 条读

对输入隐藏状态 H，CSA 算两路候选 KV（Cᵃ、Cᵇ）和对应的压缩权重（Zᵃ、Zᵇ），第 i 条压缩 KV 是

\[
C^{\text{Comp}}_i=\sum_{j=mi}^{m(i+1)-1}S^a_j\odot C^a_j+\sum_{j=m(i-1)}^{mi-1}S^b_j\odot C^b_j
\]

S 是在这 2m 个位置上逐通道做 softmax 得到的权重，并加了可学习的位置偏置（式 11–12）。也就是说，每条压缩 KV 看 2m 个 token，相邻两条有一半重叠，但条数仍是原来的 1/m。V4 取 m = 4。

选读用 V3.2 的闪电索引器：查询一侧从压缩后的查询潜向量生成 64 个索引头，与压缩后的索引键做 ReLU 打分再加权求和，取得分最高的 k 条（式 13–17；Flash k = 512，Pro k = 1024）。主注意力按 MQA（多查询注意力，一句话：所有查询头共享同一组 K、V）计算：一条压缩 KV 同时当 key 和 value，64 或 128 个查询头共用。头数多、每头 512 维，输出投影的计算量很大，所以先把头分成 g 组，每组投到 1024 维，再合并投到隐藏维（分组输出投影）。

### 2 HCA：每 128 个 token 压成一条，全部读

HCA 的压缩方式与 CSA 相同，但不重叠、压缩率 m′ = 128，压完不再挑选，所有压缩条目都参与注意力（式 20–26）。CSA 保留较细的颗粒、靠选择控制读量；HCA 颗粒很粗，但"全看一遍"不会漏掉任何一段。两种层交错排列：官方配置文件中，Flash 共 43 层，前 2 层只有滑窗，其后 21 层 CSA 与 20 层 HCA 交替；Pro 共 61 层，前 2 层为 HCA，其后 30 层 CSA 与 29 层 HCA 交替。

### 3 压缩带来的三个缺口与对应的配件（§2.3.3）

- **块内看不见。** 为保持因果性，查询只能读已经完整的压缩块，同一块里更早的 token 看不到。CSA、HCA 都加一条滑窗分支，额外读最近 128 个未压缩 token 的 KV。
- **K 兼作 V 后的位置信息。** RoPE（旋转位置编码，一句话：按位置旋转 Q、K 的分量，让点积只依赖相对距离）只作用在最后 64 维。由于同一条 KV 兼作 value，输出会带上绝对位置，作者再对输出的这 64 维施加位置为 −i 的旋转，使每条 KV 的贡献只与距离有关。
- **logit 爆炸与"无处可放"的注意力。** 注意力前对每个查询头和压缩 KV 做 RMSNorm，防止注意力分数爆炸；正因为能直接归一化 Q 和 K，V4 用 Muon 时不需要 Kimi K2 的 QK-Clip（在优化器里按注意力分数的上限缩小 Q、K 权重的做法，§2.4）。softmax 分母里加一项可学习的 exp(z′ₕ)，即 attention sink（一句话：给注意力一个"不看任何位置"的出口），一个头的注意力总量可以小于 1。

### 4 KV 缓存的账（示例数值）

推算依据：条目格式取自官方 FlashMLA 仓库的说明（V3.2 每个潜向量 656 字节：512 个 FP8、4 个 FP32 缩放因子、64 个 BF16 位置分量；V4 每条 584 字节：448 字节 FP8、128 字节 BF16、8 字节缩放因子；V4.1 的 FP4 条目 288 字节）；层的排布取自官方 config.json；索引键的字节数是我的假设（V3.2 为 128 维 FP8 加 4 字节缩放，V4 起为 128 维 MXFP4 即 64 + 4 字节）。下表的 V3.2、V4-Flash、V4.1-Flash 三行与 [V4.1-Flash](../arxiv-2609.19969/README.md) 原文图 1(b) 的 48,068、3,514、890 字节逐字节吻合；V4-Pro 一行与 V4 图 1 的"比 V3.2 小 9.5 倍"吻合。

| 模型 | 每个历史 token 存什么 | 全局 KV 字节/token | 1M（10⁶）token |
|---|---|---|---|
| V2（MLA，BF16，60 层） | 每层 576 个数 × 2 字节 | 69,120 | 69.1 GB（V2 上限 128K） |
| V3.2（MLA FP8 + 索引键，61 层） | 每层 656 + 132 字节 | 48,068 | 48.1 GB（V3.2 上限 128K） |
| V4-Pro（30 层 CSA + 31 层 HCA） | CSA 每层 (584 + 68)/4 = 163；HCA 每层 584/128 ≈ 4.6 | 约 5,031 | 约 5.0 GB |
| V4-Flash（21 层 CSA + 20 层 HCA） | 同上 | 21 × 163 + 20 × 4.56 ≈ 3,514 | 约 3.5 GB |
| V4.1-Flash（[见其精读](../arxiv-2609.19969/reading.md)） | 4 层产生全局 KV，FP4 | 890 | 约 0.89 GB |

两点读法。第一，V4 的全局 KV 几乎都在 CSA 层：HCA 的 20 层合起来每 token 只有约 91 字节。第二，单条 KV 从 V3.2 的 656 字节变为 584 字节，只省约 11%；省下的主体是条数，V3.2 每层 788 字节，V4-Flash 有全局 KV 的 41 层平均每层约 86 字节。另外，滑窗分支每层固定保存最近 128 个 token，不随长度增长；若把每个 token 的滑窗 KV 都落盘，Flash 每 token 要 43 × 584 ≈ 25 KB，约为全局 KV 的 7 倍，与原文"滑窗 KV 约为压缩 KV 的 8 倍"同一量级（§3.5.2）。

### 5 每生成一个 token 读多少（示例数值）

设上下文 L = 1,048,576，看 V4-Flash 解码一个新 token：

- CSA 层：索引器给 L/4 = 262,144 条压缩键打分，主注意力读 512 + 128（滑窗）= 640 条。
- HCA 层：不打分，主注意力读 L/128 + 128 = 8,320 条。
- 全模型：索引打分 21 × 262,144 ≈ 5.5M 次（FP4），主注意力读 21 × 640 + 20 × 8,320 ≈ 18 万条。

同样长度下 V3.2 的索引器要打分 61 × 1,048,576 ≈ 6,400 万次（FP8），主注意力读 61 × 2,048 ≈ 12.5 万条。可见 V4 省下的主要是索引器的平方项；主注意力读的总条数反而略多，多出来的在 HCA 层。按覆盖的原始位置算，Flash 每个 CSA 层读 512 条、每条约代表 4 个 token，约 2,048 个位置，与 V3.2 的 2,048 相当，只是颗粒更粗。

### 6 其余改动

- **mHC。** 残差流扩成 4 条，层间混合矩阵用 20 次 Sinkhorn-Knopp 迭代投影到双随机矩阵（每行每列之和为 1），复合映射不放大信号（§2.2）。机制见 [mHC](../arxiv-2512.24880/README.md)。V4 中它的额外时间是流水线阶段的 6.7%（§3.4.2）。
- **MoE 与路由。** 前 3 层的 MoE 不用学习的路由，按 token ID 的哈希固定分配专家；负载均衡仍是 V3 的无辅助损失偏置加一个系数 0.0001 的序列级损失。
- **Muon。** 嵌入、输出头、RMSNorm 权重和 mHC 的静态偏置与门控因子用 AdamW，其余矩阵用 Muon；正交化用 10 步 Newton-Schulz，前 8 步用快速收敛的系数，后 2 步把奇异值稳定到 1。
- **训练课程。** Flash 前 1T token 用稠密注意力预热，序列长到 64K 时先单独预热索引器，再转入稀疏训练；Pro 的稠密阶段更长，原文没有给出长度（§4.2.2）。
- **训练不稳定。** 原文承认出现了明显的损失尖峰，回滚只能暂时压住；尖峰与 MoE 层的离群值相关，路由会放大离群值。两种补丁：Anticipatory Routing（用 Δt 步之前的参数算路由，只在检测到尖峰时启用，开启时墙钟开销约 20%）；SwiGLU 截断（线性分量截到 [−10, 10]，门的上限 10）。作者写明其原理尚不清楚（§4.2.3）。

### 7 部署：缓存不再是一种

混合结构让一层里同时有压缩 KV、索引键、滑窗 KV 和"尚未凑满一块的尾部 token"。作者把滑窗与尾部当作每个请求固定大小的状态，单独分配一个状态缓存池；压缩 KV 按块分页，每块覆盖 lcm(4, 128) = 128 的倍数个原始 token（§3.5.1）。前缀复用时压缩 KV 落盘；滑窗 KV 给了全存、定期存、不存三种策略，不存时需要重算最近 n_win × L 个 token 才能精确恢复（§3.5.2）。

## 局限与后续

原文 §6 自述三点：为降低风险保留了许多初步验证过的组件和技巧，结构偏复杂，今后要精简到最本质的设计；Anticipatory Routing 与 SwiGLU 截断的原理还不清楚；下一步探索新的稀疏维度（更稀疏的嵌入模块）、更低时延的结构和多模态。

**做不好的场景（原文写明）。** 检索准确率在 128K 后可见下降（图 9）；不思考模式下 1M 任务明显变弱（表 7）；Flash 因参数少，知识类明显落后 Pro（SimpleQA-Verified Max 模式 34.1 对 57.9），高难度智能体任务也落后。真实任务评测里：最难的中文写作提示上 Claude Opus 4.5 胜率 52.0% 对 45.9%（表 14）；白领任务中偶尔忽略格式约束、不擅长把长文本压成简短摘要、幻灯片的视觉设计较弱（§5.4.3）；内部工程师调查反映会犯低级错误、误解模糊提示、偶尔想太多（§5.4.4）；用"用户消息"模拟工具交互的智能体框架（如 Terminus）走不到保留推理历史的路径（§5.1.1）；联网检索问答在"对比""推荐"两类上 V3.2 仍有竞争力（§5.4.2）。

**站在现在看：V4.1-Flash 改掉了哪些。** 五个月后的 [V4.1-Flash](../arxiv-2609.19969/README.md) 自称"精简 V4 架构"，被改掉的部件正好对应 V4 自述的"结构偏复杂"：

- HCA 整体去掉，全模型改用 CSA2；CSA 的重叠压缩、压缩时的绝对位置偏置、单独计算索引键的压缩路径都删掉（§2.3）。
- 稠密预热取消，稀疏注意力在 64K 长度上从头训练。
- MTP 从骨干预训练中去掉，改用单独训练的 DSpark 草稿器。
- `[判断]` 哈希路由大概率也被去掉：V4.1 写明"所有 FFN 都用标准 DeepSeekMoE"，官方配置里也没有 V4 的 `num_hash_layers` 字段。
- `[判断]` 查询的 RMSNorm 在 V4.1 中不再使用：官方 FlashMLA 仓库说明其融合内核中的 Q-norm"只用于 V4，不用于 V4.1"。V4 正是以"能直接归一化 Q、K"为理由不用 QK-Clip。
- 部署上，V4 提出的"滑窗 KV 不落盘、命中后精确重算"在生产中因为要重算 L × n_win 个 token 而代价过高；V4 线上部署时滑窗 KV 占持久化缓存的近一半（V4.1 §3.2.1）。这是 V4 原文没有写出、要靠下一版才暴露的坑。

**站在现在看：同期其他团队怎么选。** `[判断]` 两家在"1M 上下文要付出什么"上押了不同的注。[Kimi K3](../arxiv-2607.24653/README.md)（2026 年 7 月）沿用 [Kimi Linear](../arxiv-2510.26692/README.md) 的 3:1 混合：四分之三的层是固定大小状态的线性注意力 KDA，四分之一保留不压缩、不选择的 MLA，后者对任意历史位置都精确可读；V4 则让每一层都保留全长访问，但只读压缩或选中的条目。两家撞上了同一个工程坑：混合缓存破坏了按固定块分页的前缀缓存，V4 为此单设状态缓存池（§3.5.1），K3 因 KDA 状态只能在稀疏边界存快照，块大小被迫放大到 1024–6144 个 token（K3 §5.4.1）。两家也同时走向专家权重的 MXFP4（4 位浮点，每 32 个数共享一个缩放因子）量化感知训练与多教师 on-policy 蒸馏。K3 写明"只有长度不能带来长程能力"，并合成必须读遍 1M 才能解的任务；V4 的对应做法只写了"重视长文档数据"。更早的 [Qwen2.5-1M](../qwen2.5-1m/reading.md) 走的是推理时稀疏（训练到 256K，推理时外推并稀疏预填充），V4 则把压缩与稀疏都放进预训练。

**原文没有披露的。** 训练算力与硬件（V3 写明 2.788M H800 GPU 小时，V4 未给）；CSA/HCA 相对 DSA、mHC、Muon、哈希路由的任何消融；损失尖峰的曲线与频率；表 6 中 MRCR 的针数设置；CSA 与 HCA 的逐层排布（只在官方 config 中）。

## 批注

**易误读**

- "27% 的 FLOPs、10% 的 KV"以 V3.2 在 1M 长度下的外推值为分母，V3.2 实际只支持 128K；FLOPs 按 FP8 等效计算，路由专家的 FP4 权重在现有硬件上并不更快（§1）。
- "约为 BF16 GQA8 基线的 2%"（§2.3.4）的基线是每层 8 个 KV 头、每头 128 维、BF16，与 V3.2 的比较不是同一个分母。按上表，Flash 的 3,514 字节对 43 层 GQA8 的 176,128 字节，正好约 2%。
- "attention top-k 比 V3.2 小"指条目数；每条压缩 KV 覆盖约 4 个 token，按原始位置算覆盖范围与 V3.2 相当（Flash）或更大（Pro）。
- "前 1T token 稠密预热"只对 Flash 成立；Pro 的稠密阶段更长，原文没有给出长度。
- 官方 config 中 V4 的 RoPE 仍配置为 YaRN（原始长度 65,536，放大 16 倍），"原生支持 1M"指训练序列确实加到了 1M，并不表示位置编码不做外推。
- 表 1 的 V3.2-Base 与 V4-Base 之间同时变了数据、结构、参数与训练量，不能把差距归于某一部件。

**与其他论文的关联**

- [DeepSeek-V2 精读](../deepseek-v2/reading.md)：MLA 只压缩"每个位置存什么"，位置条数不变；V4 的 CSA/HCA 补上"条数变少"这一维。V2 精读"局限与后续"中"MLA 的边界"一条在这里兑现。
- [NSA](../arxiv-2502.11089/README.md) → [V3.2](../arxiv-2512.02556/README.md) → 本篇 → [V4.1-Flash](../arxiv-2609.19969/README.md)：训练时稀疏一路。NSA 已有"压缩块、选块、滑窗"三路，V4 把压缩与选择串起来（先压后选），滑窗保留。
- [StreamingLLM](../arxiv-2309.17453/README.md) 发现注意力会堆到开头 token 上，V4 的可学习 sink 属于"显式给出口"一路；[Gated Attention](../arxiv-2505.06708/README.md) 用门控消除汇聚，是另一路。
- [mHC](../arxiv-2512.24880/README.md) 与 Kimi 的 [Attention Residuals](../arxiv-2603.15031/README.md) 处理同一个深度方向的问题，V4 与 K3 各用了自家方案。
- [Muon](../arxiv-2502.16982/README.md) 来自 Kimi（Moonlight），V4 采用但用 Q/KV 的 RMSNorm 代替 [Kimi K2](../arxiv-2507.20534/README.md) 的 QK-Clip；V4.1 又跟进 K3 的按头分块正交化。
- [Gemma 3](../arxiv-2503.19786/README.md) 用 5:1 的局部/全局交错控制 KV；V4.1 把 V4 重新解释为"以滑窗为主干、补充压缩全局上下文"的结构，`[判断]` 两家在"局部层为主、全局层做稀疏补充"上趋同。
