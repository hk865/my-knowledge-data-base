# Kimi K2.5: Visual Agentic Intelligence

> 状态：文献卡 · 2026 · [原文](https://arxiv.org/abs/2602.02276)

[返回大语言模型目录](../../README.md) · [原文与阅读记录](source.json)

- **解决什么**：在 [Kimi K2](../arxiv-2507.20534/README.md)（1.04T 总参数、32B 激活）上加入视觉，并让智能体在宽而长的任务上不必一步一步串行做完。
- **核心方法**：文本与视觉在约 15T token 上联合继续预训练，视觉比例从低处开始早融合；只用文本 SFT（视觉推理借 IPython 操作代替）就能激活视觉推理与工具使用，作者称加入人工视觉轨迹反而损害泛化。RL 沿用 k1.5 与 K2 的策略优化，并对超出对数比区间的 token 屏蔽梯度；"Toggle"每隔若干步在"限定 token 预算内解题"与"放开长度"两个阶段之间切换，在 K2 Thinking 上把输出 token 减少 25%–30%，性能几乎不降。Agent Swarm 训练一个编排器动态拆分任务、并行派出冻结的子智能体（并行智能体 RL，PARL）：奖励含鼓励并行的实例化奖励（防止退回单智能体串行）、子任务完成率奖励（防止虚假并行）与任务结果，前两项在训练中退火到零；以"关键步数"（编排器步数加每批并行子智能体中最长的那一个）衡量延迟。WideSearch 上达到同样效果的执行时间快 3–4.5 倍；BrowseComp 从单智能体的 60.6% 提到 78.4%。作者把它看作主动的上下文管理：子智能体各自持有有限的局部上下文，只把与任务相关的结果交回编排器。
- **为什么在这个库里**：[推理时计算方向](../../fields/inference/README.md)"并行地多算"一线的公开配方（同期的 Gemini Deep Think、Muse Spark 只公开了用法），也是"思考长度变成训练目标"的 Kimi 一线在 K2 与 K3 之间的节点。优先级：选读。

## 批注

**易误读**
- "快 3–4.5 倍"按关键步数与执行时间计，不是总 token 或总算力更少：并行的子智能体合起来可能花更多 token。
