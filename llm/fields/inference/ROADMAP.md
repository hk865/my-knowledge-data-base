# 推理时计算路线图

> 状态：路线图 · v2

[入门页](README.md) · [Baseline](BASELINES.md) · [论文目录](PAPERS.md) · [草稿—验证导读](draft-verification-guide.md)

结论：五步，顺序如下：
1. 先弄清"多算"的最小单元；
2. 再把"生成得出"与"挑得出来"分开；
3. 然后看推理模型怎样把长思考训进模型；
4. 再看长思考的代价怎样控制；
5. 最后看怎样把每个 token 算得更便宜。

每一步都配一个能动手检验的问题。

## 第 1 步：多算的最小单元

读 [CoT](../../papers/arxiv-2201.11903/README.md) → [自洽](../../papers/arxiv-2203.11171/README.md)。

为什么在这里：后面所有方法都由两个最小单元组合而成。
- "多写步骤"是顺序地多算；
- "多采样投票"是并行地多算。

推理模型的长思考是前者的极限，cons@64 就是后者。先看清它们在什么规模上开始有效（CoT 约 100B），也看清在哪里饱和（自洽 5–10 条之后）。

检验：设单次采样答对的概率为 p，题目的答案只有一个。
- 估算采 N 条时"至少有一条正确"的概率：1 − (1 − p)^N。
- 再说明为什么多数投票的准确率达不到这个数：投票选的是最常见的答案，不是正确的答案。
- 最后用自洽原文的 56.5% → 74.4%，判断 PaLM 540B 在 GSM8K 上的 p 大概落在什么范围。

## 第 2 步：把"生成得出"与"挑得出来"分开

读 [Large Language Monkeys](../../papers/arxiv-2407.21787/README.md) → [Snell 等精读](../../papers/test-time-compute/reading.md)。

为什么在这里：这两篇把第 1 步的直觉变成了可测量的两条曲线。
- **覆盖率**随采样数近似对数线性增长；
- **选择**的准确率在没有可靠验证器时很快进入平台。

Snell 等进一步说明，搜索会利用验证器的错误，最优策略随难度变化。这一步之后，读任何"多算有效"的结果，都会先问：验证器是什么？

检验：用 Monkeys 的 MATH 数据回答。Llama-3-8B 的覆盖率从 82.9% 升到 98.44%，多数投票只从 40.50% 到 41.41%。中间差的这五十多个百分点，属于生成的问题还是选择的问题？再说出 Snell 等的"4 倍"有哪两笔成本没有计入（难度估计的 2048 次采样、修订模型的专门训练）。

## 第 3 步：把长思考训进模型

读 [OpenAI o1](../../papers/openai-o1/README.md) → [DeepSeek-R1](../../papers/arxiv-2501.12948/README.md)（重点读第 2 节与附录 G.2）→ [Kimi k1.5](../../papers/arxiv-2501.12599/README.md)（重点读第 2.3、2.4 节）；RL 算法本身接着读[强化学习方向](../posttraining/rl/README.md)。

为什么在这里：第 2 步留下的问题是"过程打分不可靠"。o1 给出了现象：性能随 RL 训练算力与思考时间两条轴同时提升。R1 与 k1.5 给出公开配方，两家都放弃了 PRM 与树搜索，改用可验证的结果奖励。这一步要看清两点：长思考是怎样从"答案对不对"这个稀疏信号里长出来的；为什么第 2 步的外挂搜索退到了"在长思考之上投票或重排"的位置。

检验：
- 用 R1 附录 G.2 和 k1.5 第 2.3 节，各写一句"为什么不用 PRM / 价值函数"。
- 再解释 R1 附录 F.1 的结果：同一个 Qwen2.5-32B 基座，蒸馏得 72.6%、直接 RL 只有 47.0%。这对"小模型能不能靠 RL 学会长思考"意味着什么？

## 第 4 步：控制思考长度

读 [s1](../../papers/arxiv-2501.19393/README.md) → [Overthinking](../../papers/url-https-proceedings.mlr.press-v267-chen25bx.html/README.md) → [Thinking-Optimal](../../papers/arxiv-2502.18080/README.md)；回看 k1.5 的长度奖励与 long2short。

为什么在这里：长思考是 RL 的副产品，模型不知道什么时候该停。这三篇分别回答三个问题：
- 能不能人为延长或截断思考（s1）；
- 浪费在哪里，怎样测量（Overthinking 的结果效率与过程效率）；
- 太长是否有害（Thinking-Optimal）。

它们一起划出了"推理时多算"失效的边界。

检验：在 Overthinking 的"2 加 3"例子里，第一个解就已正确，模型却写了 13 个解。用原文的结果效率定义，说明为什么这个例子的效率只有 4.3%。再对照 Thinking-Optimal 的表 2：同一模型最长一档在 GSM8K 上最差、在 AIME 上却接近最好。据此写出一条"按难度决定思考长度"的规则。

## 第 5 步：把每个 token 算得更便宜

读[草稿—验证导读](draft-verification-guide.md) → [投机解码](../../papers/arxiv-2211.17192/README.md) → [EAGLE-3](../../papers/arxiv-2503.01840/README.md) → [vLLM](../../papers/arxiv-2309.06180/README.md)；按需选读 [GQA](../../papers/arxiv-2305.13245/README.md)、[KIVI](../../papers/arxiv-2402.02750/README.md)、[BiLD](../../papers/arxiv-2302.07863/README.md)、[Judge Decoding](../../papers/arxiv-2501.19309/README.md)。

为什么在这里：前四步的方法都在增加生成的 token 数，推理模型一次回答几千到上万 token，还要多次采样。这些算力付不付得起，取决于两点：
- 每个 token 的串行步数，由投机解码处理；
- 一张卡能同时服务多少请求，由 KV 缓存管理与压缩处理。

导读先用手算讲清"输出分布为什么不变"，再看草稿器怎样越来越靠近目标模型，最后看批量对加速的影响。

检验：
- 用导读第 3 节的表，算出拒绝后应该从什么分布补 token。
- 用 Leviathan 第 3.1 节的公式 (1 − α^(γ+1)) / (1 − α)，算接受率 α = 0.75、草稿长度 γ = 7 时，每次目标模型前向平均产出多少 token。
- 解释为什么 EAGLE-3 在 vLLM 批量 56 时只有 1.01 倍。

## 动手时先查什么

比较两种推理时方法，先固定四件事：同一个生成器、同一组题、同一种选择规则、同一笔预算口径（生成次数、总 token 数或 FLOPs）。然后分开报告两个数：覆盖率和最终准确率，以区分"生成不出"和"挑不出来"。

比较两种解码加速，先固定：模型、精度、硬件、批量、输入输出长度、温度与采样方式，以及对照实现。然后分开报告：每 token 延迟、整请求延迟、吞吐。如果验证规则不是精确的，还要另测输出质量。
