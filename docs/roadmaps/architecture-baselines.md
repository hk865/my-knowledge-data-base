# 架构与推理预算 阅读路线

本组用四篇论文回答三个层次的问题：历史信息怎样流动和保存；一次前向计算怎样降低成本或增加容量；为了回答一道题，应该执行多少次生成、验证和修订。它们不是一条“Transformer → Mamba → MoE → 测试时计算”的继承链。下面的顺序是教学建议，不表示历史引用关系或直接算法依赖。

## 1 先建立注意力的共同语言

从 [Transformer精读](../deep-readings/transformer.md)开始，掌握Q/K/V、self-attention与cross-attention、因果mask、FFN，以及训练并行与自回归生成的区别。它为后续比较提供计算图基准，但原文是编码器加解码器的序列变换模型，不能直接当成所有现代decoder-only语言模型的完整配方。[原论文§3–5](https://arxiv.org/html/1706.03762v7)

读完应能回答：哪些位置互相读取？哪些向量会在解码时重复使用？FFN与attention分别负责什么？为什么信息路径短，仍可能有二次复杂度？

## 2 在两个分支里研究单次前向

第一条分支是 [Mamba精读](../deep-readings/mamba.md)：用输入条件化的状态递推处理序列，将历史压进固定大小的状态。它主要承接structured SSM、门控递推和scan相关工作；与Transformer形成替代方案比较，而不是把Transformer的某个注意力头简单改成线性attention。重点看选择性Δ/B/C、状态扩展，以及并行scan怎样降低内存读写成本。[原论文§2–3、附录B–D](https://arxiv.org/html/2312.00752v2)

第二条分支是 [DeepSeek-V2精读](../deep-readings/deepseek-v2.md)：保留Transformer的因果注意力框架，同时改变两个不同模块。MLA为每个历史token保存低维KV潜变量，缓存仍随长度增长；DeepSeekMoE在FFN里按token选择专家，降低激活计算并增加总容量。这篇是组合系统的代表baseline，MoE本身与DeepSeekMoE的前序贡献应与V2的MLA及系统实现分开。[原论文§2及附录C–D](https://arxiv.org/html/2405.04434v5)

两条分支最值得比较的是：Mamba压缩的是整段历史进入状态，MLA压缩的是每个位置的KV表示；MoE主要控制每个位置调用哪些FFN。状态大小、KV缓存、全部权重、激活参数和每token FLOPs不可互相替代。它们也不是互斥概念，但本组并未提供任意组合都有效的实验结论。

## 3 再把一次前向放进解题流程

[测试时计算精读](../deep-readings/test-time-compute.md)研究更外层的策略：固定已有模型后，在独立采样、验证器引导搜索和顺序修订之间分配预算。它不要求先采用Mamba或MoE，也没有从这两者直接派生。理解自回归生成后即可阅读；理解监督微调与奖励模型，会更容易看懂它的验证器和修订模型训练。[原论文§2–7](https://arxiv.org/html/2408.03314v1)

这层需要同时问：生成器能否产生正确候选？验证器能否选对？多次尝试是并行还是顺序？难度估计本身花多少计算？论文给出的约4倍预算效率收益有特定设置，不能与另一篇的吞吐倍数直接相乘当作已验证的联合加速。

## 4 用同一组问题做最终对照

- 信息保存：逐位置KV、逐位置压缩KV，还是固定维递推状态？
- 参数使用：每个token执行全部FFN，还是路由至部分专家？
- 解题策略：一次输出，还是多候选、搜索与修订？
- 成本口径：参数量、FLOPs、缓存、固定batch延迟、最大吞吐，还是完整解题成本？
- 证据边界：原任务与数据是否相同，训练配方是否控制，是否含量化、难度估计和验证开销？

推荐先完成Transformer，再按兴趣并行阅读Mamba与DeepSeek-V2，最后用测试时计算把“单次生成成本”与“为了答对需要多少次生成”连接起来。四篇的正文、附录覆盖和关键结果出处均附在各自精读末尾。
