# Agent 工程记忆：从一次失败到下一次可靠复用

> 速览：
> - 局部架构提供“这条经验与哪些模块有关”，任务节点提供“这次要完成什么”，记忆把过去的观察接入当前决策
> - 有价值的记录同时保留结论、证据入口、适用条件和版本；检索之后还要检查当前代码
> - 评价记忆要看后续任务是否做得更好、是否更少重复失败，以及为此多花了多少时间

## 1 记忆应该接在循环的哪里

Agent（智能体）围绕语言模型反复执行“观察环境→选择动作→读取结果”。已有基线 Reflexion 在一次失败后生成文字反思，把它交给下一次尝试；这把一次执行结果变成了后续输入。[1] 工程任务进一步要求经验能跨会话、跨文件保存，并在代码变化后重新判断用途。

**以下架构与算例是一份教学提案。** 用两个相连的视图组织问题：局部架构图描述模块、接口及依赖；任务图描述目标、子任务、尝试和验收。这里的“图”是节点与关系的表达，可以由普通文件或数据库承载。

例如，任务节点保存“修复带时区的日期解析”、当前代码基线和验收条件；它指向接口层、解析模块及回归测试。记忆记录挂到这些节点上：接口约定属于事实，某次失败属于经历，“以后先查偏移量转换”属于经验建议。节点之间的关系帮助系统找到相关记录，也帮助它在模块改动后找出需要重查的结论。

当前输入窗口是模型这次能直接看见的工作材料，持久记忆是下一次会话仍能检索的外部记录，参数记忆则由训练写入模型权重。记忆综述把载体、功能和动态过程分开讨论，说明这三种设计可以承担不同职责。[2] 下文的日期算例固定模型权重，只改变可检索记录；后面比较的研究各有不同训练设定。

## 2 一次失败怎样变成可用经验

### 第一步：保存发生了什么

设旧提交 C0 上的测试要求：把 `2026-10-05T00:30:00+02:00` 转成协调世界时 UTC 后再取日期，结果应为 10 月 4 日。程序却返回 10 月 5 日。任务节点先记录输入、期望值、实际值、运行命令、依赖版本、C0 和完整输出的位置。

“返回日期错误”是观察；“实现丢弃了时区偏移”是待检查的解释。分开两者，后续检索者就能沿证据入口检查解释，而不用把一句总结当成整个事故。PROJECTMEM 用只追加的事件保存问题、尝试、修复和决策，再生成当前摘要；“只追加”表示新事件保留旧事件的历史位置。[3]

### 第二步：把记录连回任务和结构

检查 C0 后，发现实现先截取日期再处理时区。经验可以写为：“需要按 UTC 取日历日期时，先转换时刻再取日期；证据为测试 E0，适用于解析模块的这条路径。”记录同时连接任务、函数、接口约定和测试。

这比“时区处理有坑”多了三个可操作条件：什么时候适用、去哪里检查、怎样重现。若修复后的测试通过，再追加新证据和对应提交；旧失败仍用于解释当初为什么改。PROJECTMEM 的决策替代关系保留旧决策，让当前视图指向新决策，可作为这种历史组织的参照。[3]

### 第三步：让新任务找到它

新任务 T1 要添加批量解析接口，工作从提交 C1 开始。系统先从任务节点取得目标和相关模块，再用函数名、时间语义及报错线索检索。这样即使新需求没出现原测试的句子，也能借模块关系找到 E0。

Hindsight 把世界事实、经历、归纳观察和观点分开保存，通过保留、召回、反思三个操作使用记忆；检索综合语义、关键词、图和时间线索。[4] 它提供的是“如何找到相关信息”的机制。MemRL 进一步为经验维护效用值，在语义召回后结合效用选择，并用环境反馈更新效用。[5] 这里效用回答“过去是否帮助完成任务”，事实可信度回答“这句话有什么证据”，二者应分别保留。

### 第四步：回到当前代码判断

拿到 E0 后，先查看 C1 的解析实现、接口语义和依赖版本，再运行对应测试。如果 C1 仍经过原路径，旧经验可指导新增边界测试；如果模块已重写，或者新接口明确按输入所在地取日期，就更新适用条件，并把旧结论对当前任务标成待重验或已失效。

这一步把记忆变成候选线索和验证计划。PROJECTMEM 的 precheck（编辑前历史检查）按文件调取旧问题与失败尝试，供调用者判断；其默认钩子提供警告。（它不读取新补丁的语义，也不证明两次改动等价。[3]）

### 第五步：将新结果写回

T1 完成后记录 C1 之后的新提交、实际测试回执、哪些旧经验被采用、哪些被新证据替代。经验的生命周期由新证据推动：仍适用、范围缩小、被替代。时间较久可以降低检索优先级；真正的失效依据是语义、依赖或证据发生变化。

长任务还需要决定哪些历史留在当前窗口。SWE-MeM 学习何时、压缩哪段以及怎样压缩，让记忆管理参与任务解决。[6] 在本提案中，压缩摘要用于节省当前上下文，证据入口保留在持久记录中，使下一轮仍可返回原始输出。

## 3 为什么局部架构和任务节点都重要

架构图回答“影响到哪里”，任务图回答“为什么查它”。只有模块关系，系统容易拿到大量相关却无助于当前目标的材料；只有任务摘要，系统则容易漏掉某个接口变更对下游的影响。[判断] 将两者连接，能把检索范围和重新验证范围同时落到具体对象上。

多个 Agent 共用记录时，还需要决定谁能写、哪个版本对谁可见、冲突结论怎样并存。例如两个任务在不同提交上分别观察到测试通过和失败，合并记录时应保留各自的版本条件，再由当前任务复核。计算机体系结构视角的多 Agent 记忆论文把共享与分布式存储、更新可见性和读取冲突区分开，提供了分析这些问题的语言。[7]

结构化字段使筛选和追溯可执行；真正改变行为的是“在需要时拿到有关证据，并据此改下一步”。因此可以从很小的局部图开始讨论这个机制：一个任务、一个接口、一个模块、几个测试已经足以展示完整闭环。这是理解设计的最小教学算例，是否值得扩大范围应由任务效果决定。

## 4 同一闭环怎样面对四类工程任务

- **授权范围内的网络安全分析**：任务节点保存已验证发现及其环境条件，下一步根据证据调整调查路径；AutoPentester 的任务树、结果验证与重复步骤识别提供了场景实例。[8] 从中可借用信息组织方式，授权范围和执行边界仍由独立机制管理。
- **工具调试**：模块节点可对应参数解析器、工具适配层和外部接口；历史记录保存命令、参数、返回格式及工具版本，让相同报错能回到具体调用条件。本节日期算例展示了这条路径。
- **大型系统修改**：局部图围绕本次变更的接口和依赖展开，任务节点承接跨模块的验收条件。旧决定能解释设计原因，当前集成测试检验这些理由在新版本下是否继续成立。
- **从零搭建项目**：起点是需求约束、初始接口决定和第一批测试。其他项目的经验可以作为待检验的先验；当前项目的事实从本项目的执行证据开始积累。

后面三项是把闭环迁移到场景的设计分析。它们给出了检索与核验的落点，效果仍取决于记录质量、任务相似度和验证覆盖面。

## 5 怎样知道记忆确实帮上了忙

MemoryArena 把相互依赖的子任务放在多个会话里，联合观察任务完成、子任务进度和延迟，逼系统把过去信息用于后续行动。[9] DreamBench-SWE 进一步考察：早期会话里出现、而当前代码无法重新推导的信息，是否被正确带到后续软件任务中。[10]

**作为教学用的实验设计，可比较相同模型与预算下的四种条件：无持久记忆、直接保留历史、摘要记忆、带版本与证据的检索记忆。** 重点问三件事：后续任务成功了吗；重复无效尝试和错误复用减少了吗；检索、存储及核验花费多少时间。再单独遮掉证据入口或版本条件，观察失去的是哪一种能力。这样才能区分“系统存得更整齐”和“历史真正改善了行动”。

## 批注

**易误读**

- 日期失败、双视图连接、证据失效规则和四条件比较均为本页教学设计；它们不是某篇论文已经验证的统一架构。
- PROJECTMEM v2 §6 将工作界定为可行性研究，作者使用记录不能证明其减少了重复失败；附录 B 的支付服务案例也是示例。聊天曾指向 v1，本文机制说明依据 v2。
- Hindsight §7.3 的检索预算仍有占位符，部分外部基线与该系统采用不同评判模型；跨系统排名需要更严格的匹配比较。
- MemRL 的高效用经验可能只在一类任务上有效；§6 讨论长轨迹噪声和多条经验之间的信用分配，不能把效用视为经过校准的置信度。
- 多 Agent 记忆的体系结构论文是立场与设计议程；SWE-MeM 主要考察任务进行中的上下文管理，两者均不直接验证本页的跨项目工程方案。
- MemoryArena v2 §4.1 与表格对任务模型的标签存在不一致；DreamBench-SWE 的基准发布版本与 arXiv 版本分属两套编号。本文不据此作精确模型排名或产品优劣判断。

**与其他论文的关联**

- [Reflexion](../../papers/arxiv-2303.11366/README.md) 给出“反馈→文字经验→再尝试”的基线；[PROJECTMEM](../../papers/arxiv-2606.12329/README.md) 增加工程事件的持久历史。这里是部件层面的比较，并非已证实的直接继承关系。
- [Hindsight](../../papers/arxiv-2512.12818/README.md) 与 [MemRL](../../papers/arxiv-2601.03192/README.md) 分别强调信息组织和经验选择，可共同解释检索的两个问题；[MemoryArena](../../papers/arxiv-2602.16313/README.md) 则把讨论移到后续行动效果。
